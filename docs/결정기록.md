## D-001 윈도우·맥 설치형 데스크톱 앱 (대체됨 → D-034)
- **결정**: 팀 내부 몇 명이 쓰는 설치형 앱. 사용자는 주로 윈도우, 개발은 맥.
- **이유**: 각자 PC의 GPU로 로컬 AI를 돌려야 한다. 영상을 서버에 올리지 않아도 된다.
- **버린 대안**: 웹 서비스(서버 호스팅·GPU 비용), 개인용 스크립트(팀 배포 불가).

## D-002 Java 25 + JavaFX + jpackage
- **결정**: 앱은 Java로 만들고, AI 엔진은 앱 밖(실행파일·HTTP)에 둔다.
- **이유**: 개발자의 주 언어다. 엔진을 앱 밖에 두면 앱 언어가 엔진 선택을 제약하지 않는다. Python 앱은 PyInstaller에 CUDA PyTorch를 넣으면 수 GB가 된다.
- **버린 대안**: Python + PySide6(2순위. Python 엔진을 앱 안에 넣어야 할 때만 이점), Tauri/Electron + Python(런타임 두 개, 빌드 복잡).
- **결과**: jpackage는 크로스 빌드가 안 되므로 GitHub Actions에서 OS별로 빌드한다.
- 출처: [Oracle jpackage](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html), [PyInstaller #8211](https://github.com/pyinstaller/pyinstaller/issues/8211)

## D-003 타임라인·원문은 STT에서만
- **결정**: LLM은 시간과 한국어 원문을 만들지 않는다. STT 구간 ID를 묶고, 분류하고, 번역만 한다. 결과는 코드로 검증한다.
- **이유**: 요구사항의 최우선 원칙이 정확성과 시간 정확성이다. LLM은 시간을 지어내거나 문장을 바꿀 수 있다. Gemini는 긴 오디오에서 타임스탬프가 밀린다는 보고도 있다.
- 출처: [Google AI 포럼](https://discuss.ai.google.dev/t/bug-gemini-3-flash-and-3-1-pro-progressive-timestamp-drift-in-audio-transcription/129501)

## D-004 AI 단계별 로컬/외부 선택, 로컬 먼저 구현
- **결정**: STT, 화자 구분, 구조화·번역, 화면 분석을 단계마다 로컬/외부로 고른다. 로컬 구현을 먼저 한다.
- **이유**: 비용과 성능을 모두 고려해야 한다. 같은 인터페이스로 만들면 외부 어댑터는 나중에 붙일 수 있다.
- **알고 가는 위험**: 8~10GB VRAM에서 로컬 번역 품질은 상용 모델보다 낮을 것으로 예상한다(추정). 번역 단계가 첫 외부 어댑터 후보다.

## D-005 로컬 LLM은 llama.cpp 내장
- **결정**: `llama-server`를 앱에 넣는다(윈도우 CUDA, 맥 Metal). OpenAI 호환 API로 부른다.
- **이유**: 사용자가 별도 프로그램을 설치하지 않아도 된다.
- **버린 대안**: Ollama 별도 설치(설치 단계가 하나 늘어남).
- **결과**: 바이너리 버전 고정, 모델 다운로드·체크섬 관리를 앱이 맡는다.

## D-006 로컬 STT·화자 구분 엔진 (대체됨 → D-039)
- **결정 조건**: M0 PoC에서 같은 샘플로 비교한 뒤 정한다. 방법은 설계.md 7장에 있다.
- **후보**: sherpa-onnx(Java로 바로 사용, 배포 단순) / Python 워커(Qwen3-ASR + pyannote, 정확도 근거가 가장 좋음, 별도 설치 필요).
- **이유**: 한국어 구어체, 한·일 혼합, 게임 배경음 조건의 독립 벤치마크가 없다.

## D-007 검수용 프록시 MP4
- **결정**: 영상을 불러올 때 ffmpeg로 H.264 MP4를 따로 만들어 검수 화면에서 재생한다.
- **이유**: JavaFX Media는 MKV를 재생하지 못한다. 윈도우에서 HEVC를 재생하려면 별도 확장 설치가 필요하다.
- 출처: [OpenJFX 25 javafx.scene.media](https://openjfx.io/javadoc/25/javafx.media/javafx/scene/media/package-summary.html), [JDK-8273096](https://bugs.openjdk.org/browse/JDK-8273096)

## D-008 검수는 앱에서 먼저
- **결정**: 영상과 대사 표를 나란히 놓고 앱에서 고친 뒤 시트로 내보낸다.
- **버린 대안**: 시트에서 바로 검수(만들기는 쉽지만 행에서 영상 위치로 바로 이동할 수 없다).

## D-009 시트 인증은 OAuth Desktop + `drive.file`
- **결정**: 사용자마다 자기 구글 계정으로 로그인(루프백 + PKCE). 스코프는 `drive.file`.
- **이유**: `drive.file`은 비민감 스코프라 Google 심사 부담이 적다.
- **버린 대안**: 서비스 계정(2025-04 이후 생성분은 Drive 저장공간이 없다는 2차 출처가 있다. 키 파일을 배포해야 한다).
- **미확인**: `drive.file`로 사용자가 고른 기존 폴더에 시트를 만들 수 있는지. M5에서 확인.

## D-010 OpenAI 전사 모델은 외부 STT 후보에서 제외
- **이유**: OpenAI 문서 기준 whisper-1과 4o 계열 전사 모델이 deprecated이고 2027-02-26에 종료된다. 후속 모델에는 화자 구분이 없다는 서드파티 보도가 있다.
- **남은 외부 STT 후보**: Soniox, CLOVA Speech (M6에서 비교).
- 출처: [Soniox language detection](https://soniox.com/speech-to-text/features/language-detection), [CLOVA Speech API](https://api.ncloud-docs.com/docs/ai-application-service-clovaspeech-longsentence-local)

## D-011 일본어 발화의 한국어 번역은 범위 밖
- **결정**: 요구사항 6-3의 일→한 번역은 이번 범위에서 뺀다. 나중에 구현할 때는 옵션으로 켜고 끌 수 있게 한다.

## D-012 발로란트 우선, 용어집은 게임별 파일
- **결정**: 첫 대상은 발로란트. 용어집을 게임별 파일로 나눠 다른 게임을 추가할 수 있게 한다.

## D-013 1차 배포는 미서명
- **결정**: 코드 서명 없이 배포하고 설치 안내 문서를 준다.
- **이유**: 팀 내부 몇 명만 쓴다. Azure Artifact Signing은 한국 팀이 자격 대상이 아닐 가능성이 있다(추정).
- **결과**: 윈도우는 SmartScreen 경고, 맥은 설정에서 "그래도 열기"가 필요하다.

## D-014 공개 저장소, 비공개 자료는 로컬 분리
- **결정**: GitHub 저장소는 공개. 요구사항 원문, 내부 요청서, 샘플, 평가 결과는 `docs/private/`, `samples/`, `eval/results/`에 두고 커밋하지 않는다.
- **결과**: 커밋·PR·이슈에 실제 출연자 이름이나 샘플 전사를 쓰지 않는다(AGENTS.md 절대 규칙 3).

## D-015 프로젝트 에이전트는 직접 작성
- **결정**: `spec-reviewer`, `cross-platform-checker`, `eval-runner`를 프로젝트 규칙에 맞춰 직접 쓴다. VoltAgent 모음의 `prompt-engineer`는 M3 착수 때 다듬어 추가한다.
- **이유**: VoltAgent 에이전트는 범용 템플릿이다. 근거 없는 목표 수치와 이 환경에 없는 context manager 절차가 들어 있고, 이 프로젝트 규칙은 담겨 있지 않다. JavaFX·데스크톱 Java용 에이전트는 없다.

## D-016 프로젝트 이름 koja
- **결정**: 저장소·앱 이름은 `koja`(Korean → Japanese). 데이터 폴더도 `koja`를 쓴다.

## D-017 에이전트 원본 하나, 도구별 파일은 생성
- **결정**: Claude Code, Codex, OpenCode/oh-my-opencode, Antigravity를 모두 쓴다. 공통 규칙은 `AGENTS.md`(네 도구 모두 읽음)에 둔다. 에이전트 원본은 `.agents/agents/*.md`에 두고, 나머지 도구용 파일은 `scripts/sync_agents.py`로 만든다.
- **이유**: 도구마다 에이전트 형식이 다르다. Claude Code는 `.claude/agents/*.md`, Codex는 `.codex/agents/*.toml`(`name`, `description`, `developer_instructions` 필수), OpenCode는 `.opencode/agents/*.md`(`mode: subagent`), Antigravity는 `.agents/agents/*.md`(`name`, `description` 필수)를 읽는다. 내용을 네 벌로 복사하면 어긋난다.
- **원본 위치를 `.agents/agents/`로 고른 이유**: Antigravity가 이 경로와 형식을 그대로 읽으므로, 원본이 곧 한 도구의 실제 파일이 된다.
- **버린 대안**: 도구별로 내용 전체 복사(어긋남), 원본을 Claude 형식으로 두기(Antigravity·Codex 형식과 필드가 다름).
- **미확인**: oh-my-opencode가 `.claude/agents/`도 함께 읽는다는 문서(요약본)가 있다. 그렇다면 같은 에이전트가 두 번 보일 수 있다. 실제로 겹치면 oh-my-opencode의 `claude_code.agents` 토글로 끈다.
- 출처: [Codex subagents](https://developers.openai.com/codex/subagents), [OpenCode agents](https://opencode.ai/docs/agents/), [OpenCode rules](https://opencode.ai/docs/rules/), [Antigravity subagents](https://www.antigravity.google/docs/subagents), [oh-my-openagent features](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/reference/features.md)

## D-018 결정은 즉시 기록, PR마다 문서화
- **결정**: 결정이 생기면 그 자리에서 `docs/결정기록.md`에 추가한다. PR마다 `CHANGELOG.md`의 `Unreleased`와, 바뀐 내용이 설명된 문서(설계·AGENTS·README)를 같은 PR에서 갱신한다. PR 양식(`.github/pull_request_template.md`)에 확인 항목을 둔다.
- **이유**: 여러 AI 도구와 세션이 번갈아 작업하므로, 대화에서 정한 내용이 문서에 없으면 다음 작업에서 사라진다. squash 병합으로 커밋은 PR당 하나만 남으므로 변경 요약은 CHANGELOG로 따로 관리한다.
- **버린 대안**: 커밋·PR 기록만으로 대신하기(결정 이유와 버린 대안이 남지 않음), 문서를 나중에 몰아서 정리하기(누락됨).

## D-019 저장소 줄바꿈은 LF
- **결정**: `.gitattributes`로 저장소의 텍스트 파일을 LF로 저장한다. 윈도우 전용 스크립트(`.bat`, `.cmd`, `.ps1`)만 CRLF.
- **이유**: 맥에서 개발하고 윈도우에서 빌드·실행한다. 설정이 없으면 윈도우 클론에서 줄바꿈이 바뀌어 `scripts/sync_agents.py --check`나 `gradlew`가 깨질 수 있다.

## D-020 리뷰는 작업한 도구와 다른 모델로
- **결정**: PR 전 코드 리뷰는 작업한 도구와 다른 모델로 돌린다(예: Claude Code 작업 → Codex 리뷰).
- **이유**: 네 가지 AI 도구를 함께 쓴다. 같은 모델이 쓰고 검토하면 같은 맹점을 놓친다(추정). 기존 규칙(codex-review 우선)은 Claude Code 기준이라 다른 도구에서 작업할 때 맞지 않았다.

## D-021 라이선스 (대체됨 → D-029)
- **상태**: 사용자가 나중에 정하기로 했다. 그동안 저장소는 라이선스 없음(모든 권리 보유) 상태다.
- **결정 조건**: 외부 기여를 받거나 설치파일을 배포하기 전. 같이 배포할 ffmpeg(LGPL), llama.cpp(MIT), JavaFX(GPL + Classpath Exception), 모델 가중치 라이선스와 맞춰야 한다.

## D-022 저장소 규칙은 PR 검사(CI)로 강제
- **결정**: `.github/workflows/pr-checks.yml`이 PR마다 검사한다. ① 에이전트 생성 파일 동기화 ② 비공개 경로(`docs/private`, `samples`, `eval/results`) 파일이 커밋돼 있지 않은지 ③ PR 제목이 Conventional Commits 형식인지 ④ `CHANGELOG.md`를 고쳤는지(`skip-changelog` 라벨로 예외). ①②는 main 푸시에도 돈다.
- **이유**: 문서·체크리스트만으로는 빠뜨려도 막히지 않는다. ruleset의 필수 체크로 걸면 통과해야만 병합된다.
- **강제하지 않는 것**: PR 양식의 체크박스, 결정 기록·설계 문서 갱신 여부. 기계적으로 판단할 수 없어서 리뷰에서 본다.

## D-023 Gradle 빌드 스크립트는 Kotlin DSL
- **결정**: `settings.gradle.kts`, `build.gradle.kts`로 쓴다.
- **이유**: Gradle의 현재 기본값이고, IDE 자동완성과 타입 검사로 빌드 스크립트 오타를 일찍 잡는다. 사용자 선택(2026-11-23).
- **버린 대안**: Groovy DSL(예제가 많지만 타입 검사가 없다).

## D-024 M1 설치파일은 Actions 아티팩트로만 올린다
- **결정**: M1 CI가 만든 `.msi`/`.dmg`는 워크플로 실행 아티팩트로만 올린다. 공개 Releases에는 올리지 않는다. 배포 채널 결정은 계속 보류한다.
- **이유**: 라이선스가 보류(D-021)인 상태에서 공개 Releases에 설치파일을 올리면 누구나 받는다. 아티팩트는 Releases 목록에 노출되지 않고 보관 기간이 지나면 지워진다. 다만 공개 저장소라 GitHub에 로그인한 사용자는 누구나 받을 수 있으므로 비공개 배포가 아니다. 사용자 선택(2026-11-23).
- **버린 대안**: 태그마다 GitHub Releases에 올리기(라이선스 결정 전 공개 배포), 결정 미루기(M1 CI를 만들 수 없음).

## D-025 JavaFX는 플러그인 없이 모듈 경로로 실행
- **결정**: 앱은 Java 모듈 `koja`(패키지 `koja.*`)로 만든다. JavaFX는 Gradle 플러그인 없이 Maven Central의 OS별 분류자 jar를 직접 의존한다. 버전은 JDK 25와 같은 LTS 라인인 JavaFX 25.0.x. JDK는 Gradle 툴체인(foojay)으로 맞춘다.
- **이유**: `org.openjfx.javafxplugin`은 마지막 릴리스가 0.1.0(2023-09)이라 Gradle 9와의 호환을 장담할 수 없다(추정). 분류자 지정은 빌드 스크립트 몇 줄이다. 클래스패스로 실행하면 JavaFX가 "Unsupported JavaFX configuration" 경고를 내고, main 클래스가 `Application`을 상속하면 실행이 거부된다. 모듈 경로는 이후 jpackage(jlink)와도 맞는다. 도메인이 없어 역도메인 대신 `koja`를 최상위 이름으로 쓴다.
- **버린 대안**: javafxplugin 사용, 클래스패스 실행 + 별도 `Main` 클래스, JavaFX 26/27(비-LTS).

## D-026 develop(기본) + main(릴리스) 브랜치
- **결정**: `develop`을 기본 브랜치로 두고 작업 PR은 `develop`으로 squash 병합한다. `main`은 릴리스용이고 `develop` → `main` PR을 merge commit으로 병합한다. ruleset은 브랜치마다 하나씩 둔다. 공통: PR 필수, 필수 체크 `저장소 규칙`·`빌드 (macos-latest)`·`빌드 (windows-latest)`, 강제 푸시·삭제 금지. `develop`: 선형 이력 필수, squash만. `main`: merge만, 선형 이력 규칙 없음. CI는 두 브랜치 푸시에도 돈다.
- **이유**: 사용자 요청(2026-11-23). 개발 중인 변경과 릴리스된 상태를 나눈다. squash나 GitHub의 rebase 병합으로 릴리스하면 커밋이 새로 만들어져(SHA 변경) `develop`과 `main` 이력이 갈라진다. merge commit이면 `develop`이 `main`의 조상으로 남는다. 처음엔 rebase로 정했다가 리뷰에서 이 문제가 나와 바꿨다.
- **버린 대안**: Git Flow 전체(release/*, hotfix/* — 혼자 개발에 과함), 릴리스도 squash 또는 rebase(이력 갈라짐), 관리자 우회로 `develop`을 `main`에 fast-forward 푸시(main 보호가 약해짐), main 단일 브랜치 유지.
- **참고**: 기존 ruleset은 `~DEFAULT_BRANCH` 대상이었다. 기본 브랜치를 바꾸면 main 보호가 풀리므로 `refs/heads/main`으로 고정하고 `develop` ruleset을 따로 만들었다.

## D-027 JSON은 Jackson 3, 테스트는 JUnit
- **결정**: project.json 등 JSON 읽기·쓰기는 Jackson 3.x(`tools.jackson.core:jackson-databind`)로 한다. 단위 테스트는 JUnit(Jupiter, BOM 6.x)으로 한다.
- **이유**: 표준 라이브러리에 JSON 파서가 없다. Jackson 3은 레코드를 별도 모듈 없이 다루고, 예외가 unchecked이며, JPMS 모듈 이름이 있어 모듈 경로 실행(D-025)과 맞는다. 사용자 선택(2026-11-23).
- **버린 대안**: Jackson 2.x(유지보수는 되지만 새 메이저가 3), Gson(레코드 지원이 늦고 모듈 지원이 약함 — 추정), 직접 파서.
- **참고**: Jackson 3 databind는 `com.fasterxml.jackson.annotation`(2.x 줄 jar)을 요구한다. Gradle 테스트는 클래스패스로 돌므로 `module-info`의 `opens koja.core to tools.jackson.databind`는 테스트로 검증되지 않는다. 모듈 경로에서 저장·로드가 되는 것은 수동으로 확인했다(2026-11-23).

## D-028 재생 영상은 프로젝트 폴더의 proxy.mp4, 없으면 원본
- **결정**: 프로젝트 폴더는 `project.json`이 있는 폴더다. 검수 화면은 그 폴더의 `proxy.mp4`를 재생하고, 없으면 `source.path`(상대 경로면 프로젝트 폴더 기준)를 재생한다. 재생 영상 경로는 project.json에 따로 두지 않는다.
- **이유**: 가져오기(M1 PR 5) 전에도 H.264 MP4 원본으로 검수 화면을 확인할 수 있다. 프록시 이름을 고정하면 프로젝트 폴더를 통째로 옮겨도 깨지지 않는다.
- **버린 대안**: project.json에 `proxyPath` 필드 추가(모델 버전이 바뀌고, 폴더를 옮기면 절대 경로가 깨짐), 프록시만 재생(PR 5 전에는 확인할 방법이 없음).
- **추가 의존성**: 재생에 `javafx-media`를 쓴다(JavaFX와 같은 버전).

## D-029 라이선스를 두지 않는다 (개인용)
- **결정**: 저장소에 라이선스 파일을 두지 않는다. 앱은 개인용으로 쓴다. 저장소는 공개 상태 그대로 두며, 라이선스가 없으므로 "모든 권리 보유" 상태다(남이 코드를 볼 수는 있지만 쓸 권리는 없다).
- **이유**: 사용자 결정(2026-11-23). 외부 배포나 기여를 받을 계획이 없어 지금 정할 필요가 없다. 나중에 바뀔 수 있다.
- **버린 대안**: 지금 오픈소스 라이선스 고르기(배포 계획이 없는데 ffmpeg LGPL 등과 맞추는 검토 비용이 듦).
- **결과**: 설치파일은 D-024대로 Actions 아티팩트로만 받는다. 공개 배포 채널은 두지 않는다.
- **참고**: 공개 저장소의 Actions 아티팩트는 GitHub에 로그인한 사람이면 받을 수 있다(D-024). 번들에 넣을 ffmpeg(LGPL)·llama.cpp(MIT)·JavaFX(GPL + Classpath Exception)의 고지 의무가 이 경우에도 생기는지는 확인하지 않았다(추정: 고지 파일은 넣어 두는 편이 안전하다). 배포 방식이나 공개 여부가 바뀌면 새 항목으로 다시 정한다.

## D-030 잡담 구간은 행으로 만들지 않는다 (대체됨 → D-031)
- **결정**: 인터뷰 주제와 무관한 잡담(번역가·관계자 등의 대화)은 행으로 만들지 않는다. 검수 화면과 시트에 나오지 않는다. 대신 LLM은 무시한 구간 ID를 무시 목록(`ignoredSegIds`)으로 따로 낸다. 검증은 "모든 구간 ID가 행 또는 무시 목록에 순서대로 한 번씩"으로 바꾼다. STT 구간 자체는 `sttSegments`에 그대로 남는다.
- **이유**: 사용자 결정(2026-11-23). 사람이 만든 완성 시트에는 잡담이 없고, 기록할 필요가 없다. 무시 목록을 따로 받으면 LLM이 실제 발언을 빠뜨린 것과 일부러 무시한 것을 코드로 구분할 수 있다.
- **버린 대안**: 잡담도 행으로 만들고 "제외" 표시(검수 화면에 쓸데없는 행이 늘어남), 무시 목록 없이 안 쓴 구간을 잡담으로 간주(빠뜨린 발언을 잡아낼 수 없음).
- **영향**: 절대 규칙 1(AGENTS.md, 설계 2장)과 spec-reviewer 에이전트의 검증 문구를 고쳤다. 모델 필드는 M3에서 추가한다. M0 평가에서는 시트 행과 짝이 없는 STT 구간 비율을 따로 보고해 잡담 거르기의 기준선으로 쓴다.
- **참고**: 이 관행은 요구사항 문서에 없다. 샘플(완성 시트)을 보고 사용자와 정했다.

## D-031 인터뷰 영상은 질문자·답변자 발언만 남긴다
- **결정**: 인터뷰 영상(A형)에서는 문맥을 읽어 질문자(인터뷰어)와 답변자(선수)를 가리고, 그 두 사람의 발언만 행으로 만든다. 번역가의 통역(질문을 한국어로 옮겨 말하는 것 포함)과 관계자 잡담은 행으로 만들지 않고 무시 목록(`ignoredSegIds`)에 넣는다. 검증 방식은 D-030과 같다("모든 구간 ID가 행 또는 무시 목록에 순서대로 한 번씩").
- **이유**: 사용자 결정(2026-11-23). 통역은 질문의 반복이라 필요 없다. D-030은 잡담만 다뤄 통역이 빠져 있었다.
- **버린 대안**: 통역을 질문 행에 함께 기록(시트에 없는 내용), 화자 구분 결과만으로 거르기(같은 사람이 통역과 잡담을 오가면 못 거름 — 추정).
- **적용 범위**: A형 인터뷰. B형(자유 발언)·C형(혼합)에서 누구를 남길지는 그 샘플이 생기면 정한다.
- **샘플 외부 전송**: M0 샘플 3편의 외부 AI 전송 허용 여부는 외부 어댑터(M6)를 구현할 때 정한다. 그때까지는 금지로 보고 로컬 엔진으로만 평가한다.

## D-032 목적은 편집용 초벌 기록: 빠짐없음과 시간 정확도가 먼저
- **결정**: koja의 목적은 영상의 발언을 타임테이블로 빠짐없이 기록한 초벌을 만들고, 편집자가 앱에서 고르고 고치게 하는 것이다. 사람이 최종 정제한 시트(편집에 쓸 부분만 남긴 최종본)와 같은 범위로 걸러 내지 않는다. 우선순위는 빠짐없음(재현율) → 시간 정확도 → 화자 → 문장 다듬기 순이다. 정제(불필요한 행 판단)는 LLM이 표시로 추천하는 데까지만 하고, 자동으로 지우지 않는다.
- **이유**: 사용자 결정(2026-11-23). 기존 작업은 영상을 처음부터 끝까지 보며 필요 여부를 판단하고 시간과 대사를 받아 적는 일이라 오래 걸린다. 프로그램은 이 초기 작업을 줄이는 것이 목적이다. 남는 행은 편집자가 바로 지울 수 있지만, 빠진 발언은 영상을 다시 돌려 찾아야 해서 원래 작업으로 돌아간다. 요구사항도 "모든 한국어 발화 추출", "누락 없음"을 요구한다.
- **버린 대안**: 완성 시트 수준까지 자동 정제(빠뜨리는 위험이 커지고, 무엇을 쓸지는 편집 상황마다 다름).
- **영향**: M0 평가의 1순위 지표는 정답 시트 행의 재현율과 시간 오차(1초 이내 비율)다. 정답 시트가 정제된 최종본이라, 시트에 없는 결과 행은 오류로 세지 않고 참고 수치로만 본다. 시트 문장이 다듬어져 있으면 글자 단위 정확도(CER)보다 내용이 결과에 들어 있는지를 본다. 편집자가 쓸 행을 골라 그 행만 내보내는 "사용" 체크는 검수 화면 확장 때 따로 정한다.

## D-033 무시한 구간은 검수 화면에서 접어 두고 되살릴 수 있게 한다
- **결정**: D-031의 무시 목록(`ignoredSegIds`)에 들어간 구간(통역·잡담)은 시트로 내보내지 않는다. 다만 검수 화면에서는 "숨긴 구간"으로 접어 두고, 펼쳐서 보거나 행으로 되살릴 수 있게 한다. 평소에는 접혀 있어 표에 보이지 않는다. D-031의 행 구성 규칙은 그대로다.
- **이유**: 사용자 결정(2026-11-23). LLM이 선수 발언을 잡담으로 잘못 판단해 버리면 편집자가 알 수 없다(D-032의 빠짐없음 원칙). 접어 두면 표는 깔끔하게 유지하면서 잘못 버린 발언을 되찾을 수 있다.
- **버린 대안**: 아예 보여 주지 않음(D-031 그대로, 잘못 버린 발언을 찾을 수 없음), 제외 표시를 단 행으로 항상 보여 줌(D-030 때 버린 안, 표가 지저분해짐).
- **적용 시점**: 무시 목록이 생기는 M3에서 검수 화면에 함께 넣는다.

## D-034 개인 사용 설치형 데스크톱 앱
- **결정**: 윈도우·맥 설치형 데스크톱 앱이라는 형태는 그대로 두고, 사용 범위를 "팀 내부 몇 명"에서 "개인 사용"으로 바꾼다. 사용자는 주로 윈도우, 개발은 맥이다.
- **이유**: 사용자 결정(2026-11-23). D-029(라이선스 없음)를 정하면서 실제 사용 범위가 개인이라는 점을 확인했다. 형태를 설치형 앱으로 유지하는 이유(각 PC의 GPU로 로컬 AI 실행, 영상을 서버에 올리지 않음, 검수 화면 필요)는 D-001과 같다.
- **버린 대안**: 팀 배포 전제 유지(실제 사용과 맞지 않음), 개인용이니 앱 대신 스크립트(검수 화면 없이는 초벌 기록 목적(D-032)을 못 이룸).
- **영향**: 미서명 배포 결정의 이유("팀 내부 몇 명만 쓴다")는 개인 사용에서도 그대로 성립한다. 사용자별 구글 로그인(D-009) 등 여러 사용자를 전제한 구조는 지금 바꾸지 않는다. 나중에 다시 팀 배포로 바뀌면 새 항목으로 정한다.

## D-039 로컬 STT는 whisper.cpp 내장, VAD·화자 구분은 sherpa-onnx
- **결정**: 로컬 STT는 whisper.cpp `whisper-server`(모델 large-v3-turbo)를 llama-server처럼 앱에 내장 바이너리로 넣고 HTTP로 부른다(Win CUDA / Mac Metal). VAD(Silero)와 화자 구분(pyannote segmentation-3.0 + 3D-Speaker CAM++ 임베딩, 군집 기준값 0.9)은 sherpa-onnx Java로 앱 안에서 돌린다. Python 워커는 두지 않는다. D-006을 대체한다.
- **이유**: 사용자 결정(2026-11-23). M0 PoC(맥 M5 Pro, A-1 샘플 3편, 정답 시트 비교) 결과:
  - 시트 행 재현율: whisper 2회 방식(D-040) 0.98 / 1.00 / 0.90, Qwen3-ASR 1.7B 2회 방식(Python, 10초 분할) 0.98 / 1.00 / 0.90, sherpa-onnx Qwen3-ASR 1.7B int8 0.95 / 0.98 / 0.84.
  - 시간 1초 이내 비율: whisper 0.91 / 0.70 / 0.79, Qwen 0.89 / 0.73 / 0.79, sherpa Qwen3 0.87 / 0.60 / 0.59. sherpa-onnx Qwen3-ASR은 단어 시간·언어 태그를 주지 않아(결과 객체로 확인) 구간 안 글자 비례로 추정할 수밖에 없다.

## D-040 STT는 2회(자동 언어 + 한국어 고정), 행 시각은 단어 시간
- **결정**: STT는 VAD 구간마다 자동 언어로 한 번 돌리고, 한국어가 아닌 언어로 잡힌 구간은 한국어로 고정해 한 번 더 돌린다. 두 결과를 같은 구간 ID 아래 모두 남긴다. 어느 쪽을 행으로 쓸지는 M3 구조화 단계를 설계할 때 정한다. 행 시작 시각은 VAD 구간 시작이 아니라 행 첫 단어의 STT 단어 시간을 쓴다.
- **이유**: 사용자 결정(2026-11-23, D-039와 함께). PoC에서 한 구간에 일본어 질문·통역과 짧은 한국어 답변이 섞이면, 자동 언어 판정이 구간 전체를 일본어로 정하고 한국어 답변을 일본어로 번역해 출력했다(Qwen3-ASR·whisper 모두). 이 때문에 한 샘플의 재현율이 0.74~0.76에 그쳤고, 2회 방식으로 0.87~0.90이 됐다. 한국어로만 고정하면 일본어 질문 검출이 사라진다. 말이 끊기지 않는 영상에서는 VAD 구간이 20~45초까지 길어져, 구간 시작을 행 시각으로 쓰면 1초 이내 비율이 16~62%에 그쳤다(단어 시간 사용 시 66~91%).
- **버린 대안**: 자동 언어 1회(한국어 답변 누락), 한국어 고정 1회(일본어 질문 검출 불가), 구간을 더 짧게만 자르기(10초 강제 분할로 Qwen 0.74 → 0.82까지만 개선).
- **영향**: 설계 4단계("ja 구간은 일본어로 재전사")를 이 방식으로 바꾼다. `stt.json` 구간은 언어별 텍스트를 여러 개 가질 수 있다. 구간 길이 상한(10초 강제 분할 여부)과 화자를 구간 대신 단어 시각으로 붙일지는 whisper로 앱에 붙일 때 다시 잰다.
