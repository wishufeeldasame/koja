## D-001 윈도우·맥 설치형 데스크톱 앱 (대체됨 → D-034)
- **결정**: 팀 내부 몇 명이 쓰는 설치형 앱. 사용자는 주로 윈도우, 개발은 맥.
- **이유**: 각자 PC의 GPU로 로컬 AI를 돌려야 한다. 영상을 서버에 올리지 않아도 된다.
- **버린 대안**: 웹 서비스(서버 호스팅·GPU 비용), 개인용 스크립트(팀 배포 불가).

## D-002 Java 25 + JavaFX + jpackage
- **결정**: 앱은 Java로 만들고, AI 엔진은 앱 밖(실행파일·HTTP)에 둔다.
- **이유**: 개발자의 주 언어다. 엔진을 앱 밖에 두면 앱 언어가 엔진 선택을 제약하지 않는다. Python 앱은 PyInstaller에 CUDA PyTorch를 넣으면 수 GB가 된다.
- **버린 대안**: Python + PySide6(2순위. Python 엔진을 앱 안에 넣어야 할 때만 이점), Tauri/Electron + Python(런타임 두 개, 빌드 복잡).
- **결과**: jpackage는 크로스 빌드가 안 되므로 GitHub Actions에서 OS별로 빌드한다.
- 출처: [Oracle jpackage](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html), [PyInstaller #8211](https://github.com/pyinstaller/pyinstaller/issues/8211)

## D-003 타임라인·원문은 STT에서만
- **결정**: LLM은 시간과 한국어 원문을 만들지 않는다. STT 구간 ID를 묶고, 분류하고, 번역만 한다. 결과는 코드로 검증한다.
- **이유**: 요구사항의 최우선 원칙이 정확성과 시간 정확성이다. LLM은 시간을 지어내거나 문장을 바꿀 수 있다. Gemini는 긴 오디오에서 타임스탬프가 밀린다는 보고도 있다.
- 출처: [Google AI 포럼](https://discuss.ai.google.dev/t/bug-gemini-3-flash-and-3-1-pro-progressive-timestamp-drift-in-audio-transcription/129501)

## D-004 AI 단계별 로컬/외부 선택, 로컬 먼저 구현
- **결정**: STT, 화자 구분, 구조화·번역, 화면 분석을 단계마다 로컬/외부로 고른다. 로컬 구현을 먼저 한다.
- **이유**: 비용과 성능을 모두 고려해야 한다. 같은 인터페이스로 만들면 외부 어댑터는 나중에 붙일 수 있다.
- **알고 가는 위험**: 8~10GB VRAM에서 로컬 번역 품질은 상용 모델보다 낮을 것으로 예상한다(추정). 번역 단계가 첫 외부 어댑터 후보다.

## D-005 로컬 LLM은 llama.cpp 내장
- **결정**: `llama-server`를 앱에 넣는다(윈도우 CUDA, 맥 Metal). OpenAI 호환 API로 부른다.
- **이유**: 사용자가 별도 프로그램을 설치하지 않아도 된다.
- **버린 대안**: Ollama 별도 설치(설치 단계가 하나 늘어남).
- **결과**: 바이너리 버전 고정, 모델 다운로드·체크섬 관리를 앱이 맡는다.

## D-006 로컬 STT·화자 구분 엔진 (대체됨 → D-039)
- **결정 조건**: M0 PoC에서 같은 샘플로 비교한 뒤 정한다. 방법은 설계.md 7장에 있다.
- **후보**: sherpa-onnx(Java로 바로 사용, 배포 단순) / Python 워커(Qwen3-ASR + pyannote, 정확도 근거가 가장 좋음, 별도 설치 필요).
- **이유**: 한국어 구어체, 한·일 혼합, 게임 배경음 조건의 독립 벤치마크가 없다.

## D-007 검수용 프록시 MP4
- **결정**: 영상을 불러올 때 ffmpeg로 H.264 MP4를 따로 만들어 검수 화면에서 재생한다.
- **이유**: JavaFX Media는 MKV를 재생하지 못한다. 윈도우에서 HEVC를 재생하려면 별도 확장 설치가 필요하다.
- 출처: [OpenJFX 25 javafx.scene.media](https://openjfx.io/javadoc/25/javafx.media/javafx/scene/media/package-summary.html), [JDK-8273096](https://bugs.openjdk.org/browse/JDK-8273096)

## D-008 검수는 앱에서 먼저
- **결정**: 영상과 대사 표를 나란히 놓고 앱에서 고친 뒤 시트로 내보낸다.
- **버린 대안**: 시트에서 바로 검수(만들기는 쉽지만 행에서 영상 위치로 바로 이동할 수 없다).

## D-009 시트 인증은 OAuth Desktop + `drive.file`
- **결정**: 사용자마다 자기 구글 계정으로 로그인(루프백 + PKCE). 스코프는 `drive.file`.
- **이유**: `drive.file`은 비민감 스코프라 Google 심사 부담이 적다.
- **버린 대안**: 서비스 계정(2025-04 이후 생성분은 Drive 저장공간이 없다는 2차 출처가 있다. 키 파일을 배포해야 한다).
- **미확인**: `drive.file`로 사용자가 고른 기존 폴더에 시트를 만들 수 있는지. M5에서 확인.

## D-010 OpenAI 전사 모델은 외부 STT 후보에서 제외
- **이유**: OpenAI 문서 기준 whisper-1과 4o 계열 전사 모델이 deprecated이고 2027-02-26에 종료된다. 후속 모델에는 화자 구분이 없다는 서드파티 보도가 있다.
- **남은 외부 STT 후보**: Soniox, CLOVA Speech (M6에서 비교).
- 출처: [Soniox language detection](https://soniox.com/speech-to-text/features/language-detection), [CLOVA Speech API](https://api.ncloud-docs.com/docs/ai-application-service-clovaspeech-longsentence-local)

## D-011 일본어 발화의 한국어 번역은 범위 밖
- **결정**: 요구사항 6-3의 일→한 번역은 이번 범위에서 뺀다. 나중에 구현할 때는 옵션으로 켜고 끌 수 있게 한다.

## D-012 발로란트 우선, 용어집은 게임별 파일
- **결정**: 첫 대상은 발로란트. 용어집을 게임별 파일로 나눠 다른 게임을 추가할 수 있게 한다.

## D-013 1차 배포는 미서명
- **결정**: 코드 서명 없이 배포하고 설치 안내 문서를 준다.
- **이유**: 팀 내부 몇 명만 쓴다. Azure Artifact Signing은 한국 팀이 자격 대상이 아닐 가능성이 있다(추정).
- **결과**: 윈도우는 SmartScreen 경고, 맥은 설정에서 "그래도 열기"가 필요하다.

## D-014 공개 저장소, 비공개 자료는 로컬 분리
- **결정**: GitHub 저장소는 공개. 요구사항 원문, 내부 요청서, 샘플, 평가 결과는 `docs/private/`, `samples/`, `eval/results/`에 두고 커밋하지 않는다.
- **결과**: 커밋·PR·이슈에 실제 출연자 이름이나 샘플 전사를 쓰지 않는다(AGENTS.md 절대 규칙 3).

## D-015 프로젝트 에이전트는 직접 작성
- **결정**: `spec-reviewer`, `cross-platform-checker`, `eval-runner`를 프로젝트 규칙에 맞춰 직접 쓴다. VoltAgent 모음의 `prompt-engineer`는 M3 착수 때 다듬어 추가한다.
- **이유**: VoltAgent 에이전트는 범용 템플릿이다. 근거 없는 목표 수치와 이 환경에 없는 context manager 절차가 들어 있고, 이 프로젝트 규칙은 담겨 있지 않다. JavaFX·데스크톱 Java용 에이전트는 없다.

## D-016 프로젝트 이름 koja
- **결정**: 저장소·앱 이름은 `koja`(Korean → Japanese). 데이터 폴더도 `koja`를 쓴다.

## D-017 에이전트 원본 하나, 도구별 파일은 생성
- **결정**: Claude Code, Codex, OpenCode/oh-my-opencode, Antigravity를 모두 쓴다. 공통 규칙은 `AGENTS.md`(네 도구 모두 읽음)에 둔다. 에이전트 원본은 `.agents/agents/*.md`에 두고, 나머지 도구용 파일은 `scripts/sync_agents.py`로 만든다.
- **이유**: 도구마다 에이전트 형식이 다르다. Claude Code는 `.claude/agents/*.md`, Codex는 `.codex/agents/*.toml`(`name`, `description`, `developer_instructions` 필수), OpenCode는 `.opencode/agents/*.md`(`mode: subagent`), Antigravity는 `.agents/agents/*.md`(`name`, `description` 필수)를 읽는다. 내용을 네 벌로 복사하면 어긋난다.
- **원본 위치를 `.agents/agents/`로 고른 이유**: Antigravity가 이 경로와 형식을 그대로 읽으므로, 원본이 곧 한 도구의 실제 파일이 된다.
- **버린 대안**: 도구별로 내용 전체 복사(어긋남), 원본을 Claude 형식으로 두기(Antigravity·Codex 형식과 필드가 다름).
- **미확인**: oh-my-opencode가 `.claude/agents/`도 함께 읽는다는 문서(요약본)가 있다. 그렇다면 같은 에이전트가 두 번 보일 수 있다. 실제로 겹치면 oh-my-opencode의 `claude_code.agents` 토글로 끈다.
- 출처: [Codex subagents](https://developers.openai.com/codex/subagents), [OpenCode agents](https://opencode.ai/docs/agents/), [OpenCode rules](https://opencode.ai/docs/rules/), [Antigravity subagents](https://www.antigravity.google/docs/subagents), [oh-my-openagent features](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/reference/features.md)

## D-018 결정은 즉시 기록, PR마다 문서화
- **결정**: 결정이 생기면 그 자리에서 `docs/결정기록.md`에 추가한다. PR마다 `CHANGELOG.md`의 `Unreleased`와, 바뀐 내용이 설명된 문서(설계·AGENTS·README)를 같은 PR에서 갱신한다. PR 양식(`.github/pull_request_template.md`)에 확인 항목을 둔다.
- **이유**: 여러 AI 도구와 세션이 번갈아 작업하므로, 대화에서 정한 내용이 문서에 없으면 다음 작업에서 사라진다. squash 병합으로 커밋은 PR당 하나만 남으므로 변경 요약은 CHANGELOG로 따로 관리한다.
- **버린 대안**: 커밋·PR 기록만으로 대신하기(결정 이유와 버린 대안이 남지 않음), 문서를 나중에 몰아서 정리하기(누락됨).

## D-019 저장소 줄바꿈은 LF
- **결정**: `.gitattributes`로 저장소의 텍스트 파일을 LF로 저장한다. 윈도우 전용 스크립트(`.bat`, `.cmd`, `.ps1`)만 CRLF.
- **이유**: 맥에서 개발하고 윈도우에서 빌드·실행한다. 설정이 없으면 윈도우 클론에서 줄바꿈이 바뀌어 `scripts/sync_agents.py --check`나 `gradlew`가 깨질 수 있다.

## D-020 리뷰는 작업한 도구와 다른 모델로
- **결정**: PR 전 코드 리뷰는 작업한 도구와 다른 모델로 돌린다(예: Claude Code 작업 → Codex 리뷰).
- **이유**: 네 가지 AI 도구를 함께 쓴다. 같은 모델이 쓰고 검토하면 같은 맹점을 놓친다(추정). 기존 규칙(codex-review 우선)은 Claude Code 기준이라 다른 도구에서 작업할 때 맞지 않았다.

## D-021 라이선스 (대체됨 → D-029)

- **결정 조건**: 외부 기여를 받거나 설치파일을 배포하기 전. 같이 배포할 ffmpeg(LGPL), llama.cpp(MIT), JavaFX(GPL + Classpath Exception), 모델 가중치 라이선스와 맞춰야 한다.

## D-022 저장소 규칙은 PR 검사(CI)로 강제
- **결정**: `.github/workflows/pr-checks.yml`이 PR마다 검사한다. ① 에이전트 생성 파일 동기화 ② 비공개 경로(`docs/private`, `samples`, `eval/results`) 파일이 커밋돼 있지 않은지 ③ PR 제목이 Conventional Commits 형식인지 ④ `CHANGELOG.md`를 고쳤는지(`skip-changelog` 라벨로 예외). ①②는 main 푸시에도 돈다.
- **이유**: 문서·체크리스트만으로는 빠뜨려도 막히지 않는다. ruleset의 필수 체크로 걸면 통과해야만 병합된다.
- **강제하지 않는 것**: PR 양식의 체크박스, 결정 기록·설계 문서 갱신 여부. 기계적으로 판단할 수 없어서 리뷰에서 본다.

## D-024 M1 설치파일은 Actions 아티팩트로만 올린다
- **결정**: M1 CI가 만든 `.msi`/`.dmg`는 워크플로 실행 아티팩트로만 올린다. 공개 Releases에는 올리지 않는다. 배포 채널 결정은 계속 보류한다.
- **이유**: 라이선스가 보류(D-021)인 상태에서 공개 Releases에 설치파일을 올리면 누구나 받는다. 아티팩트는 Releases 목록에 노출되지 않고 보관 기간이 지나면 지워진다. 다만 공개 저장소라 GitHub에 로그인한 사용자는 누구나 받을 수 있으므로 비공개 배포가 아니다. 사용자 선택(2026-11-23).
- **버린 대안**: 태그마다 GitHub Releases에 올리기(라이선스 결정 전 공개 배포), 결정 미루기(M1 CI를 만들 수 없음).

## D-025 JavaFX는 플러그인 없이 모듈 경로로 실행
- **결정**: 앱은 Java 모듈 `koja`(패키지 `koja.*`)로 만든다. JavaFX는 Gradle 플러그인 없이 Maven Central의 OS별 분류자 jar를 직접 의존한다. 버전은 JDK 25와 같은 LTS 라인인 JavaFX 25.0.x. JDK는 Gradle 툴체인(foojay)으로 맞춘다.
- **이유**: `org.openjfx.javafxplugin`은 마지막 릴리스가 0.1.0(2023-09)이라 Gradle 9와의 호환을 장담할 수 없다(추정). 분류자 지정은 빌드 스크립트 몇 줄이다. 클래스패스로 실행하면 JavaFX가 "Unsupported JavaFX configuration" 경고를 내고, main 클래스가 `Application`을 상속하면 실행이 거부된다. 모듈 경로는 이후 jpackage(jlink)와도 맞는다. 도메인이 없어 역도메인 대신 `koja`를 최상위 이름으로 쓴다.
- **버린 대안**: javafxplugin 사용, 클래스패스 실행 + 별도 `Main` 클래스, JavaFX 26/27(비-LTS).

## D-026 develop(기본) + main(릴리스) 브랜치
- **결정**: `develop`을 기본 브랜치로 두고 작업 PR은 `develop`으로 squash 병합한다. `main`은 릴리스용이고 `develop` → `main` PR을 merge commit으로 병합한다. ruleset은 브랜치마다 하나씩 둔다. 공통: PR 필수, 필수 체크 `저장소 규칙`·`빌드 (macos-latest)`·`빌드 (windows-latest)`, 강제 푸시·삭제 금지. `develop`: 선형 이력 필수, squash만. `main`: merge만, 선형 이력 규칙 없음. CI는 두 브랜치 푸시에도 돈다.
- **이유**: 사용자 요청(2026-11-23). 개발 중인 변경과 릴리스된 상태를 나눈다. squash나 GitHub의 rebase 병합으로 릴리스하면 커밋이 새로 만들어져(SHA 변경) `develop`과 `main` 이력이 갈라진다. merge commit이면 `develop`이 `main`의 조상으로 남는다. 처음엔 rebase로 정했다가 리뷰에서 이 문제가 나와 바꿨다.
- **버린 대안**: Git Flow 전체(release/*, hotfix/* — 혼자 개발에 과함), 릴리스도 squash 또는 rebase(이력 갈라짐), 관리자 우회로 `develop`을 `main`에 fast-forward 푸시(main 보호가 약해짐), main 단일 브랜치 유지.
- **참고**: 기존 ruleset은 `~DEFAULT_BRANCH` 대상이었다. 기본 브랜치를 바꾸면 main 보호가 풀리므로 `refs/heads/main`으로 고정하고 `develop` ruleset을 따로 만들었다.

## D-027 JSON은 Jackson 3, 테스트는 JUnit
- **결정**: project.json 등 JSON 읽기·쓰기는 Jackson 3.x(`tools.jackson.core:jackson-databind`)로 한다. 단위 테스트는 JUnit(Jupiter, BOM 6.x)으로 한다.
- **이유**: 표준 라이브러리에 JSON 파서가 없다. Jackson 3은 레코드를 별도 모듈 없이 다루고, 예외가 unchecked이며, JPMS 모듈 이름이 있어 모듈 경로 실행(D-025)과 맞는다. 사용자 선택(2026-11-23).
- **버린 대안**: Jackson 2.x(유지보수는 되지만 새 메이저가 3), Gson(레코드 지원이 늦고 모듈 지원이 약함 — 추정), 직접 파서.
- **참고**: Jackson 3 databind는 `com.fasterxml.jackson.annotation`(2.x 줄 jar)을 요구한다. Gradle 테스트는 클래스패스로 돌므로 `module-info`의 `opens koja.core to tools.jackson.databind`는 테스트로 검증되지 않는다. 모듈 경로에서 저장·로드가 되는 것은 수동으로 확인했다(2026-11-23).

## D-028 재생 영상은 프로젝트 폴더의 proxy.mp4, 없으면 원본
- **결정**: 프로젝트 폴더는 `project.json`이 있는 폴더다. 검수 화면은 그 폴더의 `proxy.mp4`를 재생하고, 없으면 `source.path`(상대 경로면 프로젝트 폴더 기준)를 재생한다. 재생 영상 경로는 project.json에 따로 두지 않는다.
- **이유**: 가져오기(M1 PR 5) 전에도 H.264 MP4 원본으로 검수 화면을 확인할 수 있다. 프록시 이름을 고정하면 프로젝트 폴더를 통째로 옮겨도 깨지지 않는다.
- **버린 대안**: project.json에 `proxyPath` 필드 추가(모델 버전이 바뀌고, 폴더를 옮기면 절대 경로가 깨짐), 프록시만 재생(PR 5 전에는 확인할 방법이 없음).
- **추가 의존성**: 재생에 `javafx-media`를 쓴다(JavaFX와 같은 버전).

## D-029 라이선스를 두지 않는다 (개인용)
- **결정**: 저장소에 라이선스 파일을 두지 않는다. 앱은 개인용으로 쓴다. 저장소는 공개 상태 그대로 두며, 라이선스가 없으므로 "모든 권리 보유" 상태다(남이 코드를 볼 수는 있지만 쓸 권리는 없다).
- **이유**: 사용자 결정(2026-11-23). 외부 배포나 기여를 받을 계획이 없어 지금 정할 필요가 없다. 나중에 바뀔 수 있다.
- **버린 대안**: 지금 오픈소스 라이선스 고르기(배포 계획이 없는데 ffmpeg LGPL 등과 맞추는 검토 비용이 듦).
- **결과**: 설치파일은 D-024대로 Actions 아티팩트로만 받는다. 공개 배포 채널은 두지 않는다.
- **참고**: 공개 저장소의 Actions 아티팩트는 GitHub에 로그인한 사람이면 받을 수 있다(D-024). 번들에 넣을 ffmpeg(LGPL)·llama.cpp(MIT)·JavaFX(GPL + Classpath Exception)의 고지 의무가 이 경우에도 생기는지는 확인하지 않았다(추정: 고지 파일은 넣어 두는 편이 안전하다). 배포 방식이나 공개 여부가 바뀌면 새 항목으로 다시 정한다.

## D-030 잡담 구간은 행으로 만들지 않는다 (대체됨 → D-031)
- **결정**: 인터뷰 주제와 무관한 잡담(번역가·관계자 등의 대화)은 행으로 만들지 않는다. 검수 화면과 시트에 나오지 않는다. 대신 LLM은 무시한 구간 ID를 무시 목록(`ignoredSegIds`)으로 따로 낸다. 검증은 "모든 구간 ID가 행 또는 무시 목록에 순서대로 한 번씩"으로 바꾼다. STT 구간 자체는 `sttSegments`에 그대로 남는다.
- **이유**: 사용자 결정(2026-11-23). 사람이 만든 완성 시트에는 잡담이 없고, 기록할 필요가 없다. 무시 목록을 따로 받으면 LLM이 실제 발언을 빠뜨린 것과 일부러 무시한 것을 코드로 구분할 수 있다.
- **버린 대안**: 잡담도 행으로 만들고 "제외" 표시(검수 화면에 쓸데없는 행이 늘어남), 무시 목록 없이 안 쓴 구간을 잡담으로 간주(빠뜨린 발언을 잡아낼 수 없음).
- **영향**: 절대 규칙 1(AGENTS.md, 설계 2장)과 spec-reviewer 에이전트의 검증 문구를 고쳤다. 모델 필드는 M3에서 추가한다. M0 평가에서는 시트 행과 짝이 없는 STT 구간 비율을 따로 보고해 잡담 거르기의 기준선으로 쓴다.
- **참고**: 이 관행은 요구사항 문서에 없다. 샘플(완성 시트)을 보고 사용자와 정했다.

## D-031 인터뷰 영상은 질문자·답변자 발언만 남긴다
- **결정**: 인터뷰 영상(A형)에서는 문맥을 읽어 질문자(인터뷰어)와 답변자(선수)를 가리고, 그 두 사람의 발언만 행으로 만든다. 번역가의 통역(질문을 한국어로 옮겨 말하는 것 포함)과 관계자 잡담은 행으로 만들지 않고 무시 목록(`ignoredSegIds`)에 넣는다. 검증 방식은 D-030과 같다("모든 구간 ID가 행 또는 무시 목록에 순서대로 한 번씩").
- **이유**: 사용자 결정(2026-11-23). 통역은 질문의 반복이라 필요 없다. D-030은 잡담만 다뤄 통역이 빠져 있었다.
- **버린 대안**: 통역을 질문 행에 함께 기록(시트에 없는 내용), 화자 구분 결과만으로 거르기(같은 사람이 통역과 잡담을 오가면 못 거름 — 추정).
- **적용 범위**: A형 인터뷰. B형(자유 발언)·C형(혼합)에서 누구를 남길지는 그 샘플이 생기면 정한다.
- **샘플 외부 전송**: M0 샘플 3편의 외부 AI 전송 허용 여부는 외부 어댑터(M6)를 구현할 때 정한다. 그때까지는 금지로 보고 로컬 엔진으로만 평가한다.

## D-032 목적은 편집용 초벌 기록: 빠짐없음과 시간 정확도가 먼저
- **결정**: koja의 목적은 영상의 발언을 타임테이블로 빠짐없이 기록한 초벌을 만들고, 편집자가 앱에서 고르고 고치게 하는 것이다. 사람이 최종 정제한 시트(편집에 쓸 부분만 남긴 최종본)와 같은 범위로 걸러 내지 않는다. 우선순위는 빠짐없음(재현율) → 시간 정확도 → 화자 → 문장 다듬기 순이다. 정제(불필요한 행 판단)는 LLM이 표시로 추천하는 데까지만 하고, 자동으로 지우지 않는다.
- **이유**: 사용자 결정(2026-11-23). 기존 작업은 영상을 처음부터 끝까지 보며 필요 여부를 판단하고 시간과 대사를 받아 적는 일이라 오래 걸린다. 프로그램은 이 초기 작업을 줄이는 것이 목적이다. 남는 행은 편집자가 바로 지울 수 있지만, 빠진 발언은 영상을 다시 돌려 찾아야 해서 원래 작업으로 돌아간다. 요구사항도 "모든 한국어 발화 추출", "누락 없음"을 요구한다.
- **버린 대안**: 완성 시트 수준까지 자동 정제(빠뜨리는 위험이 커지고, 무엇을 쓸지는 편집 상황마다 다름).
- **영향**: M0 평가의 1순위 지표는 정답 시트 행의 재현율과 시간 오차(1초 이내 비율)다. 정답 시트가 정제된 최종본이라, 시트에 없는 결과 행은 오류로 세지 않고 참고 수치로만 본다. 시트 문장이 다듬어져 있으면 글자 단위 정확도(CER)보다 내용이 결과에 들어 있는지를 본다. 편집자가 쓸 행을 골라 그 행만 내보내는 "사용" 체크는 검수 화면 확장 때 따로 정한다.

## D-033 무시한 구간은 검수 화면에서 접어 두고 되살릴 수 있게 한다
- **결정**: D-031의 무시 목록(`ignoredSegIds`)에 들어간 구간(통역·잡담)은 시트로 내보내지 않는다. 다만 검수 화면에서는 "숨긴 구간"으로 접어 두고, 펼쳐서 보거나 행으로 되살릴 수 있게 한다. 평소에는 접혀 있어 표에 보이지 않는다. D-031의 행 구성 규칙은 그대로다.
- **이유**: 사용자 결정(2026-11-23). LLM이 선수 발언을 잡담으로 잘못 판단해 버리면 편집자가 알 수 없다(D-032의 빠짐없음 원칙). 접어 두면 표는 깔끔하게 유지하면서 잘못 버린 발언을 되찾을 수 있다.
- **버린 대안**: 아예 보여 주지 않음(D-031 그대로, 잘못 버린 발언을 찾을 수 없음), 제외 표시를 단 행으로 항상 보여 줌(D-030 때 버린 안, 표가 지저분해짐).
- **적용 시점**: 무시 목록이 생기는 M3에서 검수 화면에 함께 넣는다.

CI(`build.yml`)는 `1.0.<실행 번호>`를 넘겨(윈도우 MSI는 같은 버전이면 같은 제품으로 보고 새 빌드를 덮어 설치하지 않는다) 빌드 뒤 설치파일을 만들어 `koja-<OS>` 아티팩트로 올리고 14일 보관한다.

- **참고**: 윈도우에서 `.msi`를 만들려면 WiX Toolset이 필요하다. JDK 25 jpackage가 "No JDK Modules found" 경고를 내지만, 만든 런타임에 `java.base`와 필요한 모듈이 모두 들어 있고 맥에서 .dmg를 마운트해 실행했다(2026-11-23). 설치판에서도 영상 재생이 되도록 `--enable-native-access`에 `javafx.media`를 더했다(`./gradlew run`도 같음).

## D-037 ffmpeg는 LGPL 빌드를 빌드 때 받아 번들한다
- **결정**: 설치파일에는 LGPL ffmpeg만 넣는다. 빌드(CI의 jpackage 단계) 때 고정 버전·SHA-256으로 받아 앱에 넣고, 첫 실행 때 내려받지 않는다.
  - 윈도우: BtbN/FFmpeg-Builds의 `win64-lgpl` 정적 빌드. "latest"가 아니라 월말 빌드 태그(2년 보관)를 고정한다.
  - 맥(Apple Silicon): 쓸 만한 LGPL arm64 배포판이 없어서 CI 맥 러너에서 FFmpeg 소스 태그를 `--disable-gpl --disable-nonfree --enable-videotoolbox`로 직접 빌드한다(외부 라이브러리 없음). 결과는 캐시한다.
  - 고지: 번들 옆에 FFmpeg의 `COPYING.LGPLv2.1`, 버전, 소스 주소를 적은 파일을 넣는다(D-029 참고의 "넣어 두는 편이 안전" 추정을 따름).
  - ffmpeg 위치는 `koja.runtime.Ffmpeg` 한곳에서 정한다. 지금은 환경 변수 `KOJA_FFMPEG`, 없으면 `PATH`의 `ffmpeg`를 쓴다. 번들 경로 찾기와 CI 다운로드·빌드는 jpackage PR(#6) 병합 뒤 별도 PR로 넣는다.
  - 개발 맥의 Homebrew ffmpeg(GPL, libx264 포함)는 로컬 개발에만 쓴다. 대신 앱은 libx264를 부르지 않는다(D-038). 그래야 개발 중 동작이 번들판과 같다.
- **이유**: 설계 3장("CI에서 고정 버전과 체크섬으로 받아 넣는다")과 같은 방침이다. 첫 실행 다운로드는 오프라인·실패 처리가 늘고, 고정 체크섬이면 빌드가 재현된다. BtbN은 마지막 14개 일일 빌드와 매달 마지막 빌드(2년)만 남기므로 일일 태그를 고정하면 곧 사라진다(BtbN README 확인, 2026-11-24). martin-riedl.de·osxexperts.net의 arm64 빌드는 x264·x265가 들어간 GPL 빌드이고, evermeet.cx는 인텔 전용 GPL이다(각 사이트 확인, 2026-11-24).
- **버린 대안**: 첫 실행 때 다운로드(오프라인 실패, 무결성 처리 추가), 사용자가 직접 설치(개인용이라도 경로 설정이 번거로움), GPL 빌드 번들(D-029에서 라이선스를 두지 않기로 해 GPL 조건을 검토하지 않았음), 맥에서 Homebrew ffmpeg 복사(GPL이고 dylib 의존이 많음).

## D-038 프록시 H.264 인코더는 OS별 하드웨어/OS 인코더, 모두 실패하면 프록시 없이 진행
- **결정**: libx264(GPL) 대신 아래 순서로 시도하고 처음 성공한 것을 쓴다. 순서는 `koja.runtime.Ffmpeg`에 둔다.
  - 맥: `h264_videotoolbox`(`-allow_sw 1`로 하드웨어가 안 되면 VideoToolbox 소프트웨어 인코더).
  - 윈도우: `h264_nvenc` → `h264_mf`(Media Foundation). 대상 PC가 RTX 카드라 NVENC가 먼저다.
  - 키프레임은 `-force_key_frames expr:gte(t,n_forced*1)`로 1초마다 강제한다. 프레임 수 기준인 `-g`와 달리 원본 fps를 몰라도 된다. VideoToolbox와 Media Foundation 인코더 모두 강제 키프레임(I 프레임 요청)을 처리한다(FFmpeg `videotoolboxenc.c`·`mfenc.c` 확인, 2026-11-24). NVENC는 기본값에서 강제 키프레임을 IDR이 아닌 I 프레임으로 내므로 `-forced-idr 1`을 붙인다(Codex 리뷰 지적, FFmpeg `nvenc.c`). 인코더 기본 키프레임 간격(VideoToolbox는 1초보다 짧았음)은 `-g 600`으로 꺼 둔다.
  - 모두 실패하면 프록시를 만들지 않고 경고만 띄운 뒤 가져오기를 끝낸다. 검수 화면은 D-028대로 원본을 재생한다(원본이 JavaFX가 못 여는 형식이면 재생은 안 되지만 오디오·프로젝트는 남는다).
- **이유**: 하드웨어/OS 인코더는 ffmpeg LGPL 빌드에서 쓸 수 있고 외부 GPL 라이브러리가 필요 없다. 프록시는 검수 재생용이라 화질보다 속도가 중요하다. 프록시 실패로 STT 입력(오디오)까지 버리면 다시 처음부터 해야 한다.
- **확인 못 한 것(추정)**: BtbN `win64-lgpl` 빌드에 `h264_nvenc`·`h264_mf`가 둘 다 들어 있는지는 README에서 확인하지 못했다(ffnvcodec 스크립트는 있음, Media Foundation은 확인 안 됨). 윈도우 실기에서 `ffmpeg -encoders`로 확인한다. 둘 다 없으면 BtbN에 있는 `libopenh264`(BSD)를 세 번째로 넣는 방안을 검토한다.
- **버린 대안**: libx264(GPL), 원본 그대로 재생(포맷·GOP가 제각각이라 이동이 느리거나 못 엶), 첫 인코더 실패 시 바로 가져오기 실패(오디오까지 잃음).

## D-039 로컬 STT는 whisper.cpp 내장, VAD·화자 구분은 sherpa-onnx
- **결정**: 로컬 STT는 whisper.cpp `whisper-server`(모델 large-v3-turbo)를 llama-server처럼 앱에 내장 바이너리로 넣고 HTTP로 부른다(Win CUDA / Mac Metal). VAD(Silero)와 화자 구분(pyannote segmentation-3.0 + 3D-Speaker CAM++ 임베딩, 군집 기준값 0.9)은 sherpa-onnx Java로 앱 안에서 돌린다. Python 워커는 두지 않는다. D-006을 대체한다.
- **이유**: 사용자 결정(2026-11-23). M0 PoC(맥 M5 Pro, A-1 샘플 3편, 정답 시트 비교) 결과:
  - 시트 행 재현율: whisper 2회 방식(D-040) 0.98 / 1.00 / 0.90, Qwen3-ASR 1.7B 2회 방식(Python, 10초 분할) 0.98 / 1.00 / 0.90, sherpa-onnx Qwen3-ASR 1.7B int8 0.95 / 0.98 / 0.84.

  - 화자(선수 일치율, 10초 분할 구간 기준): sherpa CAM++ 기준값 0.9 1.00 / 0.94 / 0.94, pyannote community-1 1.00 / 0.93 / 0.94. 화자를 VAD 구간 단위로 붙이면 구간이 길 때 떨어진다(whisper 2회 + CAM++, 기본 VAD: 0.94 / 0.86 / 0.85).
  - 자원: whisper-server 최대 메모리 2.0GB, Qwen(Python, MPS) 10.7~18GB, sherpa 화자 구분 0.6GB(CPU). 1시간 환산 처리 시간은 whisper 2회 약 9분, 화자 구분 약 2분(추정, 맥).

## D-040 STT는 2회(자동 언어 + 한국어 고정), 행 시각은 단어 시간
- **결정**: STT는 VAD 구간마다 자동 언어로 한 번 돌리고, 한국어가 아닌 언어로 잡힌 구간은 한국어로 고정해 한 번 더 돌린다. 두 결과를 같은 구간 ID 아래 모두 남긴다. 어느 쪽을 행으로 쓸지는 M3 구조화 단계를 설계할 때 정한다. 행 시작 시각은 VAD 구간 시작이 아니라 행 첫 단어의 STT 단어 시간을 쓴다.
- **이유**: 사용자 결정(2026-11-23, D-039와 함께). PoC에서 한 구간에 일본어 질문·통역과 짧은 한국어 답변이 섞이면, 자동 언어 판정이 구간 전체를 일본어로 정하고 한국어 답변을 일본어로 번역해 출력했다(Qwen3-ASR·whisper 모두). 이 때문에 한 샘플의 재현율이 0.74~0.76에 그쳤고, 2회 방식으로 0.87~0.90이 됐다. 한국어로만 고정하면 일본어 질문 검출이 사라진다. 말이 끊기지 않는 영상에서는 VAD 구간이 20~45초까지 길어져, 구간 시작을 행 시각으로 쓰면 1초 이내 비율이 16~62%에 그쳤다(단어 시간 사용 시 66~91%).
- **버린 대안**: 자동 언어 1회(한국어 답변 누락), 한국어 고정 1회(일본어 질문 검출 불가), 구간을 더 짧게만 자르기(10초 강제 분할로 Qwen 0.74 → 0.82까지만 개선).
- **영향**: 설계 4단계("ja 구간은 일본어로 재전사")를 이 방식으로 바꾼다. `stt.json` 구간은 언어별 텍스트를 여러 개 가질 수 있다. 구간 길이 상한(10초 강제 분할 여부)과 화자를 구간 대신 단어 시각으로 붙일지는 whisper로 앱에 붙일 때 다시 잰다.

## D-042 번들 ffmpeg 고정 버전·캐시·앱 안 위치
- **결정**: D-037을 아래처럼 구체화한다. 고정값은 `scripts/bundle_ffmpeg.sh` 한 파일에 둔다.
  - 버전: FFmpeg 9.0.2 릴리스 줄로 맞춘다. 맥은 `https://ffmpeg.org/releases/ffmpeg-9.0.2.tar.xz`(SHA-256 `8c385028…e002e`)를 빌드한다. 윈도우는 BtbN 월말 태그 `autobuild-2026-10-31-12-59`의 `ffmpeg-n9.0.2-39-g7adfbe40dc-win64-lgpl-9.0.zip`(정적 빌드, SHA-256 `9d37c564…f1a650`)을 받는다. 해시는 GitHub 릴리스 API의 digest 값이다(2026-11-24).
  - 맥 빌드 옵션: `-mmacosx-version-min=13.0`(VideoToolbox 일부 API가 13부터. JDK 25 런타임은 11), `--disable-gpl --disable-nonfree --disable-autodetect --enable-videotoolbox --enable-audiotoolbox --enable-zlib`, ffplay·ffprobe·문서는 뺀다. `--disable-autodetect`는 빌드 PC의 Homebrew 라이브러리가 몰래 링크되는 것을 막는다. 결과는 시스템 프레임워크와 `/usr/lib`만 링크한다(`otool -L` 확인).
  - 검사(스크립트 끝, 매번): `-buildconf`에 `--enable-gpl`·`--enable-nonfree`가 없고, `-L`이 LGPL이고, D-038 인코더가 모두 있어야 한다(맥 `h264_videotoolbox`, 윈도우 `h264_nvenc`·`h264_mf`). 맥은 `/opt/homebrew`·`/usr/local` 링크가 없고 최소 macOS가 13.0이어야 한다. 새로 만들 때는 임시 폴더에서 만들고 검사를 통과해야 출력 폴더를 바꾼다. 스크립트가 만든 폴더(`NOTICE.txt` 있음)나 빈 폴더가 아니면 덮어쓰지 않는다. 하나라도 어기면 CI가 실패한다.
  - 캐시: CI는 `actions/cache`로 `app/build/ffmpeg`를 `ffmpeg-<OS>-<arch>-<스크립트 해시>` 키로 캐시한다. 버전·해시를 바꾸면 스크립트가 바뀌어 다시 받거나 빌드한다. 캐시가 있어도 검사는 다시 돈다.
  - 앱 안 위치: jpackage `--app-content app/build/ffmpeg`로 넣는다. 맥은 `koja.app/Contents/ffmpeg/`, 윈도우는 `<설치 폴더>/ffmpeg/`(`koja.exe` 옆)다. 둘 다 CI가 설치파일을 풀어 확인했다(2026-11-24). 폴더에는 실행 파일, 라이선스 전문(맥 `COPYING.LGPLv2.1`, 윈도우는 BtbN의 `LICENSE.txt`), 버전·출처·해시를 적은 `NOTICE.txt`가 들어간다. BtbN LGPL 빌드는 `--enable-version3`이라 윈도우판은 LGPL 3 이상이다(BtbN `variants/defaults-lgpl.sh` 확인, Codex 리뷰 지적). 윈도우 `NOTICE.txt`에는 FFmpeg 소스 커밋(`7adfbe40dc`)과 그 시점 BtbN 빌드 스크립트 커밋 주소를 적는다.
  - 찾는 순서: `koja.runtime.Ffmpeg.executable()`은 `jpackage.app-path`(실행 파일 경로) 기준 번들 → `KOJA_FFMPEG` → PATH의 `ffmpeg` 순서로 본다.
  - `./gradlew jpackage`는 `app/build/ffmpeg`에 실행 파일과 `NOTICE.txt`가 없으면 실패한다. 번들 없는 설치파일이 몰래 만들어지지 않게 한다.
- **이유**: 9.0은 BtbN이 따로 빌드하는 최신 릴리스 줄이라 맥 소스 빌드와 같은 버전으로 맞출 수 있다. master(N-…) 빌드는 릴리스가 아니어서 맥과 맞출 수 없다. 2026-10-31 태그는 오늘(2026-11-24) 기준 가장 최근 월말 빌드라 2년 보관된다(D-037). 정적 빌드는 DLL 없이 exe 하나라 넣기 쉽다. 맥 소스 빌드는 M 시리즈 로컬에서 약 1분이라(CI 러너는 더 느릴 수 있음, 추정) 캐시로 충분하다.
- **버린 대안**: BtbN `latest`·일일 태그(사라짐), `-shared` 빌드(DLL 여러 개), Gradle 태스크 안에서 받기·빌드(윈도우에서 bash·unzip 처리와 캐시 연결이 번거로움), 번들이 없으면 경고만 하고 jpackage 진행(CI에서 빈 설치파일을 놓칠 수 있음).
- **확인 못 한 것**: PGP 서명은 확인하지 않고 SHA-256만 고정했다. macOS 13에서 실제로 실행되는지는 확인하지 않았다(빌드 메타데이터만 확인). 설치파일과 함께 대응 소스 tarball을 아티팩트로 올리는 것은 하지 않았다. 고지에 소스 주소만 적었다. 배포 범위(D-024, D-029)에서 이것으로 충분한지는 확인하지 않았다(추정). BtbN 빌드에 `h264_nvenc`·`h264_mf`가 둘 다 들어 있는 것은 CI의 `-encoders`로 확인했다(D-038의 추정 해소, 2026-11-24). 윈도우 실기 RTX 3080 데스크톱에서 설치판의 번들 ffmpeg로 `h264_nvenc` 인코딩(720p 테스트 영상 5초)이 되는 것을 확인했다(2026-11-24). 같은 PC에서 설치판 앱으로 가져오기 → 검수 화면 재생까지 됐고, 만들어진 `proxy.mp4`의 encoder 태그로 `h264_nvenc`가 쓰인 것을 확인했다(720p 60fps). 다른 윈도우 PC 확인은 D-043에 따라 하지 않는다.

## D-044 번역 기본 모델은 Gemma 4 E4B, 26B-A4B는 선택 설치
- **결정**: 로컬 번역 기본 모델은 Gemma 4 E4B(Q4_K_M, 전부 GPU)로 한다. Gemma 4 26B-A4B는 사용자가 따로 골라 받는 선택 모델로 둔다(기본 다운로드에 넣지 않는다). D-041의 보류를 끝낸다.
- **이유**: 사용자 결정(2026-11-25). 윈도우 RTX 3080 실측(D-041)에서 chrF 평균은 E4B 29.3, 26B 29.5로 거의 같고, 영문 고유명사 유지와 행 대응 실패 0건도 같았다. 처리 시간은 E4B가 1시간 영상에 3.1분, 26B가 8.6분이다. 자원은 E4B가 VRAM 3.4GB, 26B가 VRAM 8.1GB + RAM 19.5GB다. 8GB 카드 기준(AGENTS.md 절대 규칙 5)에 E4B는 여유가 있고, 26B는 8GB에서 재지 않았다.
- **버린 대안**: 26B 기본(맥 정성 확인에서 게임 롤 이름을 업계 표기로 더 잘 옮겼지만 약 3배 느리고 8GB 미확인), E4B만(10GB 이상 PC에서 품질을 더 보고 싶을 때 받을 길이 없어짐).
- **한계**: chrF는 다듬은 시트 일본어 대비 참고 지표이고 샘플 3편이다. 용어 차이는 게임별 용어집(D-012)으로 줄인다(추정). 26B를 고른 8GB 카드에서의 속도는 모른다.

## D-045 한국어 후보가 있는 구간은 일본어 질문 행과 한국어 행에 함께 쓸 수 있다
- **결정**: 구조화 검증(D-030·D-031의 "모든 구간 ID가 행 또는 무시 목록에 순서대로 한 번씩")에 예외를 하나 둔다. 2회 방식으로 한국어 후보가 붙은 구간(D-040)은 QUESTION_JA 행 하나(1차 결과의 일본어)와 한국어 행(LINE·QUESTION_KO) 하나에 함께 쓸 수 있다. 한국어 행끼리, QUESTION_JA 행끼리, 무시 목록 안에서는 여전히 한 번씩·오름차순이고, 무시한 구간은 행에 쓸 수 없다. 나머지 D-030·D-031 내용은 그대로다.
- **이유**: 사용자 결정(2026-11-25). VAD 구간이 길어(평균 6~10초, 최대 45초) 한·일이 섞인 한 구간에 일본어 질문과 한국어 답변이 같이 든다. 2회 방식이 두 결과를 남기는 이유가 이것이다. 엄격 규칙에서는 둘 중 하나가 빠지고(D-032 빠짐없음 위반), M0 구조화 비교에서 E4B가 이 구간을 질문·답변 양쪽에 써서 첫 샘플 6청크 중 3청크가 3번 안에 검증을 통과하지 못했다(설계 7.3).

## D-048 단계 결과 파일 stt.json·diar.json 스키마, 한국어 후보는 구간 안 `ko`, project.json 선택 항목은 버전을 올리지 않는다

D-040의 두 번째 결과는 언어별 목록이 아니라 구간 안 `ko`(`text`, `words`) 하나로 둔다. 단어 시간은 `{startMs, endMs, text}`. 화자 턴의 `speaker`는 엔진 임의 라벨이고, 화자표 id(`S1` …)로 바꾸는 건 파이프라인이다. 읽기·쓰기 때 구간 id 오름차순·구간과 단어의 시간 범위를 검사하고, 읽을 때 빠진 항목을 거부한다(빠진 시간이 0으로 읽혀 검사를 통과하는 것을 막음). 화자 구분을 새로 돌리면 그 라벨 id의 화자표 항목을 미확인으로 다시 만든다.
- **결정(버전 정책)**: `project.json`에 항목을 더할 때 옛 파일에 없어도 되는 선택 항목이면 `version`을 1로 둔다. 없으면 빈 값으로 읽는다(리스트는 `[]`, 객체는 null). 이번에 `ignoredSegIds`(D-033), `sttSegments[].words`·`ko`(D-040)를 이렇게 넣었다. 옛 파일을 못 읽게 되는 변경(필수 항목 추가, 의미·형식 변경)에서만 버전을 올리고, 그때 옮기는 코드를 같이 넣는다.
- **이유**: 2회 방식은 "1차 결과 + 한국어 고정 후보"뿐이라 두 번째 결과는 언제나 한국어다(D-040). 목록으로 두면 LLM 입력·검증(D-045)에서 "한국어 후보가 있나"를 매번 찾아야 한다. 같은 레코드를 쓰면 `stt.json` → `project.json` 변환이 화자 붙이기 하나로 끝난다. 엔진 출력은 믿지 않고 검사한다. id가 틀리면 행 검증(D-045)이 엉뚱한 구간을 가리킨다.
- **이유(버전 정책)**: M1에서 저장한 프로젝트(구간·행이 빈 파일 포함)를 그대로 열어야 한다. 버전을 올리면 지금 검사(정확히 1)가 옛 파일을 거부한다. 선택 항목은 빈 값이 곧 "아직 그 단계를 안 돌림"이라 옮길 내용이 없다. W3-2(무시 목록 화면)와 `Project` 레코드가 충돌하지 않도록 자리를 먼저 만든다(작업 계획).
- **버린 대안**: `alternatives: [{lang, text, words}]` 목록(일반적이지만 쓰는 경우가 한국어 하나뿐), 단계 결과를 `project.json`에만 저장(단계를 다시 돌릴 때 엔진 출력 원본이 남지 않음), 화자 턴을 처음부터 `S1` 형식으로(엔진마다 라벨 규칙이 달라 매핑이 엔진 안으로 들어감). 버전 정책: 항목마다 버전 올리기(옮기는 코드만 늘어남), 새 항목을 별도 파일로(프로젝트 상태가 여러 파일로 흩어짐).

## D-049 엔진은 단계마다 열고 닫고, 파이프라인은 끝난 단계를 건너뛴다
- **결정**: `Transcriber`·`Diarizer`·`LlmClient`·`FrameReader`는 `koja.engine.Engine`(`AutoCloseable` + `name()`)을 잇는다. 파이프라인(`koja.engine.Pipeline`)은 단계 직전에 엔진을 열고(`Opener`) 단계가 끝나면 try-with-resources로 닫은 뒤 다음 단계 엔진을 연다. 실행 전체(읽기~마지막 저장)를 앱 전체 잠금 하나로 감싸 여러 실행이 겹쳐도 엔진은 하나만 열리고 같은 프로젝트 파일을 엇갈려 고치지 않는다. 진행률 콜백 안에서 다시 실행하면 거부한다. 단계가 끝나면 결과 파일을 쓰고 `stages.<단계>`를 `done`으로 저장한다. 다시 돌릴 때 `done`이고 결과 파일이 있으면 건너뛴다. 진행률은 `DoubleConsumer`, 취소는 스레드 interrupt(`InterruptedException`)다. 파이프라인은 설계 3장의 `core`가 아니라 `engine` 패키지에 둔다.
- **이유**: GPU는 한 번에 한 단계만(AGENTS.md 절대 규칙 5, 8GB 카드). 엔진 객체 수명을 단계 하나로 묶으면 닫기를 빠뜨릴 수 없다. 1시간 영상에서 STT만 수 분이 걸려(D-039 실측) 화자 구분에서 실패했을 때 STT를 다시 돌리지 않아야 한다. 파이프라인이 엔진 인터페이스를 직접 쓰므로 `engine`에 두면 `core`(모델·저장)가 `engine`을 몰라도 된다.
- **버린 대안**: 엔진을 앱 시작 때 한 번 만들어 계속 쓰기(GPU를 쥔 채 다음 단계로 감), 진행·취소용 별도 리스너 타입(`Importer.Listener`처럼 단계 이름이 필요한 곳은 파이프라인 `Listener` 하나로 충분), `CompletableFuture` 기반 비동기 API(단계가 순차라 이점이 없음).
- **남긴 것**: 화자 수 범위 지정(설계 4장 3단계), LLM 응답 형식(JSON 스키마), 행 만들기와 STT를 다시 돌렸을 때 기존 행 처리는 이 계약에 아직 없다. 필요한 작업(W2-3, M3, W2-4)에서 인터페이스에 더한다.

## D-050 모델 다운로드(ModelStore)는 Java HttpClient + Range 이어 받기 + SHA-256 + 원자적 이동
- **결정**: 대용량 모델은 외부 도구(curl·Python)를 부르지 않고 Java 표준 `java.net.http.HttpClient`(`module-info.java`에 `java.net.http` 추가)로 직접 받는다. 대상 파일과 같은 폴더의 `<파일>.part`에 스트리밍으로 기록하고, 같은 경로의 동시 다운로드는 프로세스 내부 락 + OS `<파일>.lock` 파일 잠금으로 직렬화한다. 취소·연결 끊김·응답/본문 수신 시간 초과 시 `.part`를 남겨 다음 호출에서 `Range: bytes=<오프셋>-`로 이어 받는다(`Content-Range` 오프셋 일치 확인, 200 응답 시 처음부터 덮어쓰기, 416 시 `.part` 삭제 후 1회 재시도). 수신이 끝나면(완성 `.part` 재사용 포함) `fsync` 뒤 스트리밍 SHA-256을 검증하고 `ATOMIC_MOVE`로 최종 경로에 옮긴다. 체크섬이 다르면 `.part`를 삭제하고 실패한다.
- **이유**: 외부 의존성 없이 윈도우·맥에서 동일하게 동작하고, 수 GB 모델 다운로드가 중단돼도 처음부터 다시 받지 않는다. `ProjectStore`(D-027)와 같은 원자적 이동 방침으로 반쪽·손상 파일이 최종 모델 위치에 남지 않게 한다.
- **버린 대안**: 외부 `curl`·Python 프로세스 호출(진행률·취소 제어와 크로스 플랫폼 오류 처리가 복잡), 비원자적 덮어쓰기(중단 시 손상된 모델이 정상으로 오인됨), 체크섬 검증 생략(전송 손상·변조를 잡지 못함).

## D-051 로컬 서버(LocalServer)는 127.0.0.1 동적 포트·프록시 우회·프로세스 트리 종료 대기
- **결정**: `whisper-server`와 `llama-server`는 공통 `koja.runtime.LocalServer`로 실행·종료한다. `127.0.0.1`에서 빈 포트를 동적 할당하거나 자식이 직접 바인딩한 포트를 로그에서 추출(`portFromLog`)하며, 준비 완료 전 리스너가 실제로 이 프로세스 트리 소유인지 확인한다(맥 `lsof`, 윈도우 `netstat`). 로컬 호출용 `HttpClient`는 `ProxySelector.of(null)`로 시스템 프록시를 끈다. 표준 출력·오류는 UTF-8 가상 스레드로 비워 파이프 막힘을 막고 최근 로그만 링 버퍼에 남긴다. 헬스체크(`HealthCheck`)는 `startupTimeout` 남은 시간 안에서만 실행하며, 통과 전 프로세스가 종료되면 즉시 실패한다. 시작·대기 중 하위 프로세스(`ProcessHandle.descendants()`)를 누적 추적하고, 종료(`close`) 시 하위 조회 실패와 무관하게 루트·하위 프로세스를 정상 종료 유예 뒤 강제 종료(`destroyForcibly`)한다. 강제 종료 후에도 생존 프로세스가 남으면 예외로 알려 다음 GPU 단계 진입을 막고, JVM 종료 훅으로 비정상 종료 시 좀비 프로세스를 방지한다.
- **이유**: 고정 포트는 이미 떠 있는 다른 서버에 원문을 보낼 위험이 있고, 동적 포트 사전 할당도 TOCTOU 창에서 다른 서버에 오연결될 수 있다. 시스템 `HTTP_PROXY`가 켜져 있으면 로컬 요청이 외부로 새어 절대 규칙 3(비공개 샘플 외부 전송 금지)을 어길 수 있다. 종료 완료 확인 없이 다음 단계를 시작하면 8GB VRAM 카드에서 이전 엔진의 GPU 메모리가 해제되지 않아 OOM이 발생한다(절대 규칙 5).
- **버린 대안**: 고정 포트 사용(포트 충돌·오연결 위험), 소유권 검증 없는 사전 포트 할당(다른 서버 오연결 위험), `destroy()` 호출 후 즉시 반환(GPU 메모리 해제 전 다음 단계 진입 위험), OS별 `taskkill`/`pkill` 셸 명령 호출(인젝션·OS 분기 부담; 프로세스 종료는 Java `ProcessHandle` 표준 API로 처리).

## D-053 구조화 출력 형식은 2단계 분석 + 구간 1:1 평탄 고정 순서 JSON 스키마
- **결정**: 5단계 구조화(Gemma 4 E4B 기본, D-046)의 입출력 형식을 다음 두 단계로 확정한다. 절대 규칙 1(LLM 출력에 시간·원문 금지, 구간 ID만 참조, D-045 예외)을 유지한다.
  1. **1단계(영상 전체 분석)**: 화자별 발화 시간·언어 시간 비율·화자 전환 통계·대표 발화와 영상 25%·60% 지점의 연속 대화 발췌를 LLM에 한 번 보내 `videoType`(`INTERVIEW_JA | INTERVIEW_KO | FREE | MIXED`)과 화자별 추정 역할(`INTERVIEWER_JA | INTERVIEWER_KO | INTERVIEWEE | INTERPRETER | STAFF | UNKNOWN`)을 판별한다(사용자가 가져올 때 영상 유형을 지정하면 그 값을 우선).
  2. **2단계(청크 구조화)**: 기존 중첩 그룹핑(`rows[{kind, segIds}]` + `ignoredSegIds`)을 버리고, 청크 입력 구간과 **1:1 고정 순서 배열**인 평탄 JSON 스키마 `{"items": [{"id", "action", "newRow", "flags"}]}`(`minItems == maxItems == len(ids)`)로 받는다.
     - `action`: `LINE | QUESTION_KO | QUESTION_JA | BOTH_JA_LINE | IGNORE`. `FREE` 영상에서는 질문 액션(`QUESTION_JA`, `QUESTION_KO`, `BOTH_JA_LINE`)을 스키마에서 제외해 자유 발언형에 질문 영역이 생기지 않게 한다(요구사항 7-1). `BOTH_JA_LINE`은 한국어 후보가 있는 구간(D-045)이 청크에 있을 때만 허용한다.
     - `newRow`: 새 행 시작 여부(boolean).
     - `flags`: `SPEAKER_UNSURE`, `TEXT_UNSURE` 배열.
  3. **코드 검증·결정 변환·대체**: `items`의 `id` 배열이 요청 구간 ID와 정확히 같은 순서·개수인지, `BOTH_JA_LINE`이 한국어 후보 보유 구간에만 쓰였는지 검증한다. 통과하면 코드가 `rows`·`ignoredSegIds`로 결정 변환하되, 한국어 행(`LINE`·`QUESTION_KO`)은 화자 변경·앞 구간 문장 끝 부호(`.?!。？！`)·길이 상한(누적 16한글자·4.5초 이상 또는 합산 32한글자 초과)에서 `newRow=false`여도 새 행으로 분리해 과병합을 막는다(요구사항 5-3·8-4). `QUESTION_JA`는 질문 완결 단위로 묶는다. 화자 미배정(`?`)·비한국어 2한글자 미만 한국어 행에는 코드로 `SPEAKER_UNSURE`·`TEXT_UNSURE`를 보강한다(절대 규칙 2). 변환 결과는 D-031·D-045 불변식으로 이중 검증한다. 실패 시 깨진 JSON을 누적하지 않고 최신 오류와 정확한 ID 목록만 넘겨 최대 3회 재시도하고, 그래도 실패하면 청크 구간을 하나씩 `LINE`으로 남긴다(D-032).
- **이유**: 맥 M5 Pro + Gemma 4 E4B(Q4_K_M, `--reasoning off`, 샘플 3편, 설계 7.3) 실측에서 기존 그룹 스키마의 검증 1회 통과율 `9/19(47%)`·`4/19(21%)`(대체 청크 2·5개)가 평탄 스키마로 **`42/42(100%)`·`51/51(100%)`(재시도 0·대체 청크 0)**까지 올랐다. 1단계 영상 분석에 언어 시간 비율과 연속 대화 발췌를 넣어 통역사 화자를 식별함으로써 그 외 화자(통역·관계자) 무시율이 `0~7%`에서 `22~42%`로 개선됐고, 과병합 방지 가드로 행 경계 1:1이 기준선을 상회했다.
- **버린 대안**: 기존 중첩 그룹 스키마 유지(4B 모델에서 구간 ID 누락·역전 빈발), 화자 역할만으로 통역을 코드에서 무조건 삭제(화자 구분 오류 시 선수 답변 누락 위험, D-031·D-032 위반), `newRow`를 전적으로 LLM에만 위임(2차 실험에서 6~13구간 과병합으로 시간 1초 이내·1:1 지표 하락).
- **한계**: 샘플 3편이 모두 A-1형(일본인 인터뷰어)이라 B형(자유 발언)·C형(혼합)·A-2형(한국인 인터뷰어) 실측은 샘플 확보 후 확인해야 한다. 일본어 질문 오검출률(`0.52~0.78`)과 일부 통역 한국어 잔존은 검수 화면(D-033)으로 보완한다. 윈도우 8GB/10GB 실기에서는 구조화를 아직 재지 않았다.

## D-054 구조화 입력 단위는 1차 언어 인식 문장·화자·한국어 절 분할(`clause`), 기본 VAD 유지
- **결정**: 5단계 구조화 직전에 코드가 STT 단어 시간과 화자 턴으로 구간을 **1차 언어 인식 문장·화자·한국어 절 단위(`clause`)**로 나눈 뒤 단위 ID를 매겨 LLM에 넘긴다.
  - 한국어 구간(`lang == "ko"`): 문장 끝 부호(`.?!。？！`), 단어 화자 전환(1초 이상), 쉼표·250ms 휴지(8한글자 이상), 한국어 종결어미(10한글자 이상)·연결어미(14한글자 이상), 최대 24한글자에서 분할.
  - 비한국어 구간(`lang != "ko"`): 2차 한국어 후보(`koWords`)의 환각 문장부호로 자르지 않고, 1차 단어의 화자 전환(1.5초 이상) 또는 긴 문장 끝(8초 이상)에서만 분할.
  - 분할 조각에 화자가 비면 부모 구간 화자를 상속한다(부모도 없으면 `?` + `SPEAKER_UNSURE`).
  - 모든 텍스트와 `startMs`(첫 단어 시간)는 STT 단어에서만 오므로 절대 규칙 1을 지킨다.
  - 구조화의 기본 입력 STT는 **기본 VAD(2회 방식)**를 유지한다. 10초 VAD 강제 분할(`vad10`) 최종 채택 여부는 M2(W2-3)에서 화자 구분 파라미터와 함께 결정한다.
- **이유**: 기존 문장 조각(`KOJA_SPLIT=1`)은 `ja` 구간도 2차 한국어 후보 부호로 잘라 일본어 질문 검출이 `0.50 / 0.47 / 0.30`으로 무너지고 토큰이 `7,355`까지 늘었다. `clause` 분할 + 평탄 스키마(`e4b@v3_clause`, 기본 VAD)는 D-032 1·2순위 지표인 **시트 행 재현율 `0.982 / 1.000 / 0.868`**, **시간 1초 이내 `0.727 / 0.411 / 0.667`**(기존 `0.182 / 0.268 / 0.567` 대비 대폭 상승), **행 경계 1:1 `0.564 / 0.464 / 0.545`**(기존 `0.073 / 0.179 / 0.567`)를 기록했고 1시간 영상 환산 **8.7분**이다. `vad10 + clause`(`e4b@v3_clause_vad10`)는 일본어 질문 검출(`0.900 / 0.789 / 0.957`)과 그 외 화자 무시(`0.220 / 0.335 / 0.415`), 영상 유형 일치(3/3)에서 뚜렷이 유리하지만 강제 절단과 단위 증가로 재현율이 소폭 내려가고(`0.982 / 0.982 / 0.816`) 구조화 시간이 `11.7분`으로 늘어난다. D-032 우선순위(재현율·시간 우선)에 따라 기본 VAD + `clause`를 기본으로 두고 `vad10`은 M2에서 STT·화자와 함께 최종 판단한다.
- **버린 대안**: 원본 VAD 구간 그대로(`none`: 시간 1초 이내 `0.18~0.57`, 행 경계 1:1 `0.07~0.57`로 자막 행 단위 미달), 기존 문장 조각(`sent`: 일본어 질문 파괴), 10초 VAD를 지금 전면 강제(재현율 소폭 손실·처리 시간 증가).

## D-055 구조화 청크는 최대 24구간·3분, 앞뒤 최대 6구간(30초) 문맥, 컨텍스트 8K
- **결정**: 구조화 청크 상한을 기존 "4분 고정(구간 수 무제한), 컨텍스트 16K"에서 **최대 24구간 또는 3분(180초) 중 먼저 도달하는 지점**, 앞뒤 문맥 **최대 6구간(30초 이내)**, `llama-server` 컨텍스트 **8192(8K)**로 확정한다. 청크 끝에 걸친 행과 그 시작 ID 이후의 행·무시 구간은 확정하지 않고 다음 청크에서 다시 묻는다(`settle`).
- **이유**: 시간만 4분으로 자르면 분할 뒤 청크당 구간이 60~80개로 늘어나 프롬프트가 `7,355`토큰에 달하고 E4B 1회 통과율이 `4/19(21%)`로 떨어졌다. 28구간 상한(2차 실험)에서도 1편의 1청크에서 ID 불일치 재시도 3회(대체 청크 1개)가 발생했으나, **24구간**으로 낮춘 3차 실험에서는 기본 VAD(`42/42`)·`vad10`(`51/51`) 모두 **100% 1회 통과, 최대 프롬프트 토큰 2,580~2,590**으로 안정화됐다. 8K 컨텍스트에서 E4B GPU 메모리는 `4.0~4.4GB`(맥 추정, 기존 16K 5.4GB 대비 감소)로 8GB VRAM 카드(절대 규칙 5)에 여유가 있고 번역 단계(7.2, 8K)와 같은 설정이라 단계 사이에 `llama-server`를 재기동하지 않고 이어 쓸 수 있다.
- **버린 대안**: 4분 고정 + 16K 컨텍스트(구간 수 폭증 시 검증 실패·VRAM 증가), 28구간 상한(1청크 대체 발생), 청크 끝 행 재질의 생략(청크 경계에서 질문·문장 절단).

## D-056 토큰·키 보관: 맥 security CLI, 윈도우 PowerShell DPAPI
- **결정**: `koja.runtime.SecretStore` 하나로 감싼다. 맥은 Keychain에 `security` CLI로 넣고 뺀다. 값은 `security -i`의 표준 입력으로 넘겨 프로세스 인자(ps)에 보이지 않게 한다. 윈도우는 `powershell.exe`에서 .NET `ProtectedData`(DPAPI, CurrentUser)로 암호화한 base64를 `%LOCALAPPDATA%\koja\secrets\<이름>.dpapi`에 둔다. 값은 역시 표준 입력으로 넘긴다. 리프레시 토큰만 저장하고 액세스 토큰은 메모리에만 둔다.
- **이유**: 둘 다 OS에 기본으로 있어 새 의존성이 없다(AGENTS.md). DPAPI 파일은 같은 윈도우 사용자만 풀 수 있어 Credential Manager와 보호 수준이 비슷하다(추정).
- **버린 대안**: JNA(새 의존성, 네이티브 라이브러리 번들), `cmdkey`(저장만 되고 비밀번호를 다시 읽지 못함), PowerShell에서 Credential Manager P/Invoke(`Add-Type`이 호출마다 C#을 컴파일해 느림, 추정), Java KeyStore 파일(그 파일의 암호를 또 어딘가 둬야 함).
- **한계**: `security -w`는 ASCII가 아닌 값을 16진수로 돌려줘 맥은 출력 가능한 ASCII만 받는다(토큰·API 키는 ASCII). 호출마다 프로세스를 하나 띄운다(윈도우 PowerShell 시작이 수백 ms, 추정). 저장·조회는 로그인·내보내기 때만 해서 괜찮다고 본다. 윈도우 DPAPI는 CI 윈도우 러너 단위 테스트로만 확인했고 실기 확인은 아직이다.

## D-057 `drive.file` 시트 위치는 실제 로그인 PoC 뒤에 정한다
- **상태**: 보류. 실제 구글 로그인을 하지 못했다(PoC 작업 환경에 OAuth 클라이언트와 브라우저 로그인이 없음).
- **확인 방법**: `./gradlew oauthPoc --args="<기존 폴더 ID>"`(설계 9장). 내 드라이브 루트, 사용자가 내 드라이브에서 만든 기존 폴더(공유 드라이브는 범위 밖), 앱이 만든 폴더 세 곳에 시트를 만들어 HTTP 결과를 본다.
- **예상**: Google 문서상 `drive.file`은 앱이 만들었거나 사용자가 Picker로 앱에 연 파일만 다룬다. 기존 폴더를 `parents`로 주면 404/403일 것이다(추정, 미확인). 그렇다면 후보는 (1) 앱이 만든 `koja` 폴더나 루트에 만들기, (2) Google Picker로 폴더를 고르게 하기(웹 페이지·API 키가 필요해 무거움)다.
- **결과(2026-11-25 실측, 맥, 사용자 본인 계정 1개)**: 위 "상태"는 실측 전 기록이다. 실제 브라우저 로그인 후 `oauthPoc`를 1회 돌렸다. 로그인·키체인 저장 성공, 시트 생성은 내 드라이브 루트, 사용자가 드라이브 웹에서 만든 기존 폴더, 앱이 만든 폴더, 그 안 모두 HTTP 200, 만든 파일 4개 삭제는 모두 204. 실측이 위 "예상"(기존 폴더는 404/403일 것, 문서상 불가로 추정)을 뒤집었다.
- **결정**: 시트는 사용자가 고른 기존 폴더(내 드라이브)에 `drive.file`로 바로 만든다. 폴더를 고르지 않으면 내 드라이브 루트에 만든다. Picker·앱 전용 폴더는 쓰지 않는다. 폴더 ID를 받는 UI는 W5-2에서 정한다.
- **이유**: 실측에서 추가 권한·Picker 없이 됐다. 스코프를 넓히지 않아도 된다(D-009).
- **한계**: 내 드라이브 폴더 한 개, 계정 한 개, 1회만 쟀다. 공유 드라이브 폴더, 다른 사람 소유 폴더(공유받은 폴더), Workspace 등 다른 계정 유형은 재지 않았다. 앞으로 Google 정책이 바뀌어 거절되면(403/404) 루트에 만들고 그 사실을 사용자에게 알리는 대비가 필요하다(추정).

## D-058 구글 OAuth 클라이언트는 환경 변수·시스템 속성으로 받는다
- **결정**: 클라이언트 ID·시크릿은 `KOJA_GOOGLE_CLIENT_ID`·`KOJA_GOOGLE_CLIENT_SECRET` 환경 변수, 없으면 시스템 속성 `koja.google.clientId`·`koja.google.clientSecret`에서 읽는다. 저장소에는 넣지 않는다.
- **이유**: 공개 저장소다(D-014). 데스크톱 클라이언트의 시크릿은 배포물에 들어가 비밀로 취급되지 않는다고 Google이 설명하지만, 저장소에 두면 다른 사람이 같은 클라이언트로 할당량을 쓸 수 있다.
- **남은 일**: 설치판에 클라이언트를 넣는 방법(CI 비밀값에서 jpackage `--java-options`로 주입 등)은 M5 내보내기(W5-2) 때 정한다.

## D-060 윈도우 GPU는 CUDA 12.4(Vulkan 아님), CUDA 런타임 DLL은 `<설치 폴더>/cuda/` 한곳에 두고 whisper·llama가 함께 쓴다
- **결정(백엔드, 설계 9장 미결 해소)**: 윈도우 whisper-server는 공식 CUDA 12.4 빌드를 쓴다. Vulkan 빌드는 쓰지 않는다.
- **결정(CUDA DLL 공유 위치)**: CUDA 런타임 DLL `cudart64_12.dll`·`cublas64_12.dll`·`cublasLt64_12.dll`은 `<설치 폴더>/cuda/`(`koja.exe` 옆, `whisper/`·`llama/`와 같은 높이) 한곳에 둔다. 서버 실행 파일 폴더에는 그 서버의 `ggml*.dll`만 둔다(whisper.cpp와 llama.cpp의 `ggml*.dll`은 버전이 달라 한 폴더에 섞지 않는다). 서버를 띄울 때 `cuda/`를 자식 프로세스 `PATH` 맨 앞에 붙인다(`koja.runtime.WhisperServer.environment`). 윈도우는 변수 이름이 보통 `Path`이고 Java 자식 환경 맵은 대소문자를 가려서, 부모 환경의 실제 이름(대소문자 무시로 찾음)으로 덮어쓴다. `PATH`로 넣으면 두 변수가 함께 넘어가 `cuda/`가 빠질 수 있다(Codex 리뷰 지적). `cuda/`는 `scripts/bundle_whisper.sh`가 whisper zip에서 꺼내 `app/build/cuda`에 만들고, `cuda/NOTICE.txt`(NVIDIA CUDA EULA 부록 A 재배포 파일)와 EULA 전문 `cuda/LICENSE.txt`를 둔다. 전문은 NVIDIA 재배포 목록 `redistrib_12.4.1.json`의 `cuda_cudart`·`libcublas` `license_path`(같은 파일)에서 받아 SHA-256을 고정한다. 버전 없는 주소라 NVIDIA가 고치면 해시가 달라져 스크립트가 멈춘다(그때 해시를 새로 확인한다). **W3-1(llama-server)은 CUDA 12.x 빌드를 쓰고 CUDA DLL을 따로 넣지 않으며, 같은 `cuda/`를 같은 방법(PATH 앞)으로 쓴다.** llama.cpp가 CUDA 13 등으로 바뀌어 DLL 이름이 달라지면 이 결정을 다시 쓴다.
- **이유**: 크기(b5907, 압축 해제 기준): `ggml-cuda.dll` 570MB, `cublasLt64_12.dll` 474MB, `cublas64_12.dll` 100MB, `cudart64_12.dll` 0.5MB. whisper 쪽 전체 약 582MB + CUDA 런타임 약 575MB. CUDA 런타임은 llama-server도 똑같이 필요해서(poc/win_setup.py는 llama용 cudart zip 391MB를 따로 받음) 한곳에 두면 설치파일이 약 575MB(압축 전) 줄어든다. ggml은 백엔드 DLL을 `LoadLibrary`로 읽고, 거기에 링크된 DLL은 윈도우 표준 검색 순서(실행 파일 폴더 → 시스템 폴더 → 현재 폴더 → `PATH`)로 찾으므로 `PATH` 앞에 두면 찾는다(Microsoft 문서 기준, 실기 미확인). 시스템 `PATH`는 바꾸지 않고 자식 프로세스 환경만 바꿔 다른 프로그램에 영향이 없다. Vulkan: b5907 릴리스에 윈도우 Vulkan 빌드가 없어 CI에서 Vulkan SDK로 직접 빌드해야 하고, NVIDIA 카드(대상 장비, D-043)에서 Vulkan 속도는 재지 않았다. CUDA는 대상 PC에서 RTF 0.048~0.057을 쟀다(D-039). Vulkan은 cuBLAS가 필요 없어 설치파일이 크게(약 1GB) 작아질 것으로 보지만(추정, 미측정), 실측 없이 바꿀 이유가 없다.
- **버린 대안**: CUDA DLL을 서버 폴더마다 넣기(약 575MB 중복), 두 서버를 한 폴더에(`ggml*.dll` 충돌), Vulkan 빌드(직접 빌드·속도 미측정), CUDA 11.8 빌드(zip에 cuBLAS가 없어 사용자 PC에 CUDA Toolkit이 있어야 함, 2026-11-26 zip 목록 확인), 사용자에게 CUDA Toolkit 설치 요구.
- **확인 못 한 것**: (1) `PATH` 앞에 둔 `cuda/`에서 `ggml-cuda.dll`의 cuBLAS가 실제로 읽히는지. CI 러너에는 NVIDIA 드라이버(`nvcuda.dll`)가 없어 CUDA 백엔드가 아예 안 읽혀 확인할 수 없다. 윈도우 실기 확인이 필요하다. (2) whisper·ggml DLL은 VC++ 런타임(`MSVCP140`·`VCRUNTIME140`·`VCRUNTIME140_1`·`VCOMP140`)을 읽는다. 번들하지 않았다. 대상 PC(RTX 3080 데스크톱)에서 같은 zip이 돌았으므로 그 PC에는 있다. 없는 PC에서는 서버가 시작하지 못한다(추정). 필요해지면 VC++ 재배포 DLL을 `whisper/`에 넣는다. (3) 설치파일(.msi) 크기·설치 시간은 CI 결과로 본다.

## D-061 `WhisperTranscriber`: VAD는 주입, 구간마다 자동 언어 → 한국어가 아니면 한국어 재전사, 언어는 코드로
- **결정**: `koja.engine.whisper.WhisperTranscriber`가 `Transcriber`를 구현한다.
  - VAD는 생성자로 받는다(`WhisperTranscriber.Vad`: audio → 시작 순 `Span(startMs, endMs)` 목록). sherpa-onnx Silero VAD 구현은 W2-3이 만들고 W2-4가 연결한다.
  - VAD 구간마다 audio.wav에서 그 구간을 잘라(`Wav`, 16kHz 모노 16비트 PCM만 받음) `POST /inference`(multipart, `response_format=verbose_json`, `temperature=0`)로 `language=auto` 1회. 결과 언어가 `ko`가 아니면 같은 구간을 `language=ko`로 1회 더 보내 `ko` 후보(`text`, `words`)로 남긴다(D-040). PoC `merge_2pass.py`와 같은 규칙이다.
  - 1회차 텍스트가 비면 그 구간은 `stt.json`에 넣지 않는다. 구간 id는 넣은 구간만 1부터 매긴다. 2회차가 비면 `ko`는 null.
  - 언어: whisper-server(b5907)는 `language`에 전체 이름(`korean`, `japanese`)을 준다(맥 실측). `korean→ko`, `japanese→ja`, `english→en`, `chinese→zh`로 바꾸고, 그 밖은 이름을 그대로 둔다.
  - 단어 시간: `segments[].words[]`(서버가 UTF-8 경계로 토큰을 합친 것)의 `start`·`end`(초)에 구간 시작을 더해 ms로 바꾸고, 구간 `[startMs, endMs]` 안으로 묶는다. 빈 토큰은 뺀다. 구간 `startMs`·`endMs`는 VAD 구간(파일 길이로 자름)이다.
  - 진행률은 VAD 전 -1, 이후 처리한 구간 수 / 전체. 구간 사이에 interrupt를 보고, HTTP 요청은 `sendAsync`를 기다리다 interrupt면 취소한다. WAV는 `RandomAccessFile`로 읽는다(`FileChannel`은 interrupt에 `ClosedByInterruptException`을 던져 D-049 취소 계약과 어긋남). `close()`가 서버를 내린다(D-049, 절대 규칙 5). 서버 시작(모델 로드) 중 interrupt는 `LocalServer`가 `CancellationException`으로 알리므로 `Pipeline`이 엔진을 열 때 `InterruptedException`으로 바꾼다(Codex 리뷰 지적). 응답에 `text`가 없으면(형식이 다른 서버) 무음으로 보지 않고 실패한다. `name()`은 `whisper.cpp large-v3-turbo 2pass`.
- **이유**: VAD를 주입받으면 W2-3과 병렬로 만들 수 있고, 테스트에서 가짜 VAD·가짜 서버 응답으로 2회 방식 병합을 검증할 수 있다. 실측 전에는 `language`를 짧은 코드로 봤는데(PoC 매핑 표는 둘 다 받음), 짧은 코드를 가정하면 한국어 구간까지 모두 재전사됐다(맥 2분 샘플 실측에서 발견, 2026-11-26). 토큰 시각은 추정값이라 구간 밖으로 조금 나갈 수 있어 `stt.json` 검사(D-048)를 통과하도록 묶는다.
- **버린 대안**: whisper-server 내장 VAD(`--vad`)(요청 하나에 언어를 한 번만 정해 구간별 언어 인식이 안 됨), 전체 파일 업로드 + `offset`(1시간이면 요청마다 115MB), 한국어 고정 결과를 별도 구간으로 추가(D-048이 구간 안 `ko`로 정함), 빈 1회차 구간을 빈 행으로 남기기(내용 없는 행만 늘어남).
- **확인**: 맥(M5 Pro)에서 직접 빌드한 whisper-server로 A-1 샘플 앞 2분(PoC Silero VAD 구간 8개)을 전사해 `stt.json` 검사를 통과했고, 한국어 3구간은 재전사하지 않고 비한국어 5구간에만 `ko` 후보가 붙었다. 서버 준비 약 1~6초, 전사 약 9초. 맥 설치판(.dmg) 안의 whisper-server를 앱 경로 규칙(`jpackage.app-path`)으로 찾아 같은 방식 전사(앞 30초)가 됐고, 끝난 뒤 서버 프로세스가 남지 않았다.

## D-062 sherpa-onnx Java 2.0.3은 GitHub Releases에서 직접 받아 빌드 때 명시 모듈화하고 네이티브는 `sherpa-native`로 번들한다
- **결정**:
  1. **의존성 획득**: `sherpa-onnx` v2.0.3(`sherpa-onnx-jvm`, 플랫폼별 `sherpa-onnx-native-lib-<platform>`)은 Maven Central에 없고 JitPack에서도 v2.0.3 빌드가 실패하므로, Gradle `ivy` 저장소로 공식 GitHub Releases(`k2-fsa/sherpa-onnx`)에서 직접 받고 모든 jar의 SHA-256을 검증한다.
  2. **JPMS·jpackage 호환**: `sherpa-onnx-jvm-2.0.3.jar`는 자동 모듈(`module-info.class` 없음, 의존 모듈은 `java.base`뿐, 단일 패키지 `com.k2fsa.sherpa.onnx`)이라 `jpackage` 내부 `jlink`가 거부한다. Gradle `modularizeSherpaJvm` 태스크가 JDK 25 `javac --patch-module`·`jar --update`로 `module sherpa.onnx.jvm { exports com.k2fsa.sherpa.onnx; }`를 주입해 명시 모듈로 바꾼다.
  3. **네이티브 라이브러리 로딩**: `sherpa-onnx-native-lib-*` jar는 파일 이름에 Java 키워드 `native`가 들어가 JPMS 모듈 경로에 올릴 수 없다(`FindException`). 전용 Gradle 구성(`sherpaNative`)으로 받아 동적 라이브러리(`libonnxruntime.dylib`·`libsherpa-onnx-jni.dylib` / `onnxruntime.dll`·`sherpa-onnx-jni.dll`)와 라이선스 원문(`LICENSE-sherpa-onnx.txt`, `LICENSE-onnxruntime.txt`, `ThirdPartyNotices-onnxruntime.txt`, `NOTICE.txt`)을 `app/build/sherpa-native`에 넣는다. 개발 실행·테스트는 `-Dsherpa_onnx.native.path`, 설치판은 jpackage `--app-content`로 맥 `Contents/sherpa-native`·윈도우 `<설치 폴더>/sherpa-native`에 넣고 `koja.engine.SherpaNative`가 `AppPaths.bundledDirectory("sherpa-native")`로 지정한다. `--enable-native-access`에 `sherpa.onnx.jvm`을 더한다. `./gradlew build`의 `verifyModuleNativeLoad` 태스크가 JPMS 모듈 경로에서 네이티브 로딩을 매번 검증한다.
  4. **모델 파일과 오디오 읽기**: ONNX 모델 3종(`silero_vad.onnx`, Hugging Face 커밋 고정 `pyannote-segmentation-3-0/model.onnx`, `campplus_zh_en.onnx`)은 `koja.runtime.ModelStore`(D-050)로 SHA-256 검증 뒤 내려받는다. WAV 파일은 C++ JNI `WaveReader` 대신 순수 Java `WavAudio`(`Files.newInputStream`)로 읽어 한글·공백 경로와 취소(interrupt)를 안전하게 처리하고, 모델 파일도 JNI 호출 전에 존재·크기·SHA-256을 검증한다(C++ `AssertFileExists`의 `exit(-1)`·미처리 예외로 JVM이 종료되는 것 방지).
- **이유**: JavaFX·jpackage의 순수 JPMS 구성(D-025·D-035)을 깨뜨리지 않고 외부 Gradle 플러그인 없이 해결한다. `sherpa_onnx.native.path`로 직접 적재하면 실행마다 임시 폴더에 DLL을 풀지 않아 윈도우에서 잠긴 DLL 임시 폴더가 쌓이는 문제도 피한다. v2.0.3은 `poc/` 버전과 같고 CAM++ 패딩 정리(#4201)·클린 발화 임베딩 군집(#4240)이 포함돼 있다.
- **버린 대안**: JitPack 의존(v2.0.3 빌드 실패, 제3자 빌드 의존), 클래스패스 기반 jpackage 전환(D-025 JavaFX 모듈 경로 방침 위반), `badass-jlink` 같은 외부 Gradle 플러그인 추가(D-035와 같은 이유로 배제), 런타임에 jar 리소스에서 임시 폴더로 매번 추출(윈도우 DLL 삭제 불가로 임시 파일 누적).
- **한계**:
  - `sherpa-onnx` 2.0.3 C++ `OfflineSpeakerDiarization::Process()`는 진행 콜백의 반환값을 무시하므로 네이티브 화자 구분 도중 들어온 취소(interrupt)는 계산이 끝난 직후 `InterruptedException`으로 반영된다(WAV 읽기와 `Vad.detect`는 즉시 중단). 1시간 영상 기준 최대 약 1.6~1.7분(맥)~4분(윈도우) 대기가 생길 수 있어, 추후 업스트림 중단 API가 생기거나 UI 취소가 불편하면 보완한다.
  - `sherpa-onnx` 2.0.3 JNI는 모델 경로를 수정 UTF-8(`GetStringUTFChars`)로 넘겨 이모지 등 보조 평면 문자가 든 모델 폴더 경로에서는 실패할 수 있다(한글·일본어·공백 등 BMP 경로와 `WavAudio` 오디오 경로는 문제없음).
- **확인 범위**: 맥 arm64에서 `./gradlew build`(JPMS `verifyModuleNativeLoad` 포함) 및 `.dmg` 번들·패키징 실행으로 확인(2026-11-26). 윈도우 x64는 CI 빌드·`verifyModuleNativeLoad`·`.msi` 번들 검증으로 확인하고 실기 실행은 사용자가 나중에 확인한다.

- **한계**: A-1 샘플 3편(같은 인터뷰어) 기준이라 다인 자유 대화(B형)에서 군집 기준값이 달라질 수 있다. 그때는 화자 수 지정(`numClusters`) 또는 설정 노출로 대응한다.

## D-066 `LlamaServerClient`는 OpenAI 호환 API·JSON 스키마 강제·`--reasoning off`·`-ngl auto`·8K 컨텍스트·Gemma 4 E4B 기본/26B 선택
- **결정**: `koja.engine.LlmClient`에 `Request`(다중 메시지 `messages`, 선택 `jsonSchema`, `temperature`, `maxTokens`)와 `Response`(`content`, `usage`, `finishReason`), `ContextLengthExceededException`, `OutOfMemoryException`, `OutputTruncatedException`을 정의하고 기존 `complete(system, user)`는 기본 메서드로 유지한다. `LlmClient`에는 Jackson 타입을 노출하지 않고 `jsonSchema`를 JSON 문자열로 받는다.
  - 로컬 구현 `LlamaServerClient`는 `ModelStore`(D-050)로 고정 리비전·SHA-256의 GGUF(`LlamaModel.GEMMA_4_E4B` 기본, `GEMMA_4_26B` 선택, D-044·D-046)를 준비하고 `LocalServer`(D-051)로 `llama-server`를 `--host 127.0.0.1 --port 0 -ngl auto -c 8192 -np 1 --reasoning off --log-verbosity 3`로 띄운다. 부모 환경의 `LLAMA_ARG_*`·`LLAMA_LOG_*`·`LLAMA_API_KEY`(원격 터널·로그 억제·인증 강제 등)는 자식 프로세스에서 제거하고, `extraArgs`는 로컬 추론 튜닝 옵션(`--n-cpu-moe`, `--threads`, `--batch-size`, `--seed`, `--flash-attn`, `--cache-type-k/v`, `--fit-target/ctx`, `--mlock`/`--mmap`/`--no-mmap`)만 허용한다.
  - 서버가 로그에 출력한 `listening on http://127.0.0.1:<port>` 문구에서만 실제 바인딩 포트를 추출(`portFromLog`)하고 `/health` `{"status":"ok"}`로 준비 완료를 확인한다.
  - 호출은 `/v1/chat/completions`에 `stream: false`, `jsonSchema`가 있으면 `response_format: {type: "json_schema", json_schema: {name: "response", strict: true, schema: ...}}`로 보낸다. 스키마 요청이 `finish_reason: "length"`로 잘리면 `OutputTruncatedException`으로 실패시킨다.
  - `close()`가 `LocalServer` 프로세스 트리를 종료·확인해 단계 종료 시 GPU 메모리를 해제한다(절대 규칙 5).
- **이유**: `--port 0` 로그 추출은 사전 포트 할당의 TOCTOU 창을 없애고 `LocalServer`(D-051) 소유권 검증과 맞는다. `-ngl auto`(`--fit on` 기본)는 8~10GB 카드에서 E4B 전부 GPU, 26B MoE 전문가 일부 CPU 자동 배치를 D-041에서 실측 확인했다. 8K 컨텍스트·`--reasoning off`는 구조화(D-055)·번역(7.2) 공통 설정이라 5·7단계가 같은 설정을 공유한다.
- **버린 대안**: 사전 할당 포트(`--port <allocated>`, TOCTOU 가능), `-ngl 99` 고정(8~10GB 카드에서 26B OOM), `LlmClient` 시그니처에 Jackson `JsonNode` 노출(외부 어댑터·호출부 결합 증가).

## D-067 `LlamaServerClient` 오류·재시도 정책: 일시 오류만 재시도, 컨텍스트 초과·OOM은 즉시 실패
- **결정**: `LlamaServerClient`는 HTTP `429`·`502`·`503`·`504`와 서버 프로세스가 살아 있을 때의 일시 통신 오류(`HttpTimeoutException` 제외)만 기본 최대 2회(총 3회) 재시도한다.
  - 컨텍스트 초과(`exceed_context_size_error` 등)는 `ContextLengthExceededException`(`promptTokens`, `contextSize` 포함)으로 즉시 실패한다.
  - 시작 실패·HTTP 오류 본문·서버 종료 로그에서 OOM 패턴이 감지되면 `OutOfMemoryException`으로 즉시 실패한다.
  - 그 외 4xx 클라이언트 오류, 타임아웃, 서버 프로세스 종료는 재시도하지 않고 즉시 실패하며, 스레드 interrupt 시 진행 중인 요청을 취소하고 `InterruptedException`을 던진다.
- **이유**: 컨텍스트 초과와 OOM은 같은 요청을 되풀이해도 풀리지 않으며, 상위 단계(5단계 구조화·7단계 번역)가 청크를 줄이거나 모델 변경을 안내해야 한다. 반면 `llama-server`의 일시 503(슬롯 대기·로딩)은 짧은 대기 뒤 재시도로 복구된다.
- **버린 대안**: 모든 오류 일괄 재시도(컨텍스트 초과·OOM에서 불필요한 대기), 재시도 없음(일시 503 취약), 클라이언트 내부 임의 프롬프트 절단(절대 규칙 1·D-032 누락 위험).

## D-069 `llama-server` 번들을 jpackage·CI에 연결하고 윈도우 CUDA 런타임 DLL은 공유 `cuda/`로 통합한다
- **결정**: D-065에서 W2-2b 병합 뒤로 미룬 `llama-server`의 jpackage·CI 연결과 윈도우 CUDA 런타임 DLL 공유 배치를 D-059·D-060 패턴에 맞춰 확정한다.
  - `scripts/bundle_llama.sh`는 `OUT`(기본 `app/build/llama`)과 `CUDA_OUT`(생략 시 `OUT` 형제 `cuda/`, 기본 `app/build/cuda`) 2인자를 받는다. 윈도우 `llama/`에는 `llama-server.exe`와 llama·ggml·OpenMP DLL, `LICENSE`, `LICENSE-LLVM-OpenMP`, `NOTICE.txt`만 넣고 CUDA 런타임 DLL(`cudart64_12.dll`·`cublas64_12.dll`·`cublasLt64_12.dll`)은 중복 복사하지 않는다.
  - `CUDA_OUT`에 `bundle_whisper.sh` 등이 만든 유효한 공유 `cuda/`(`CUDA_FILES` + NVIDIA 공식 EULA `LICENSE.txt` + `NVIDIA CUDA `로 시작하는 `NOTICE.txt`)가 이미 있으면 덮어쓰지 않고 그대로 재사용한다. 단독 실행으로 `CUDA_OUT`이 비어 있을 때만 `cudart-llama-bin-win-cuda-12.4-x64.zip`과 NVIDIA 공식 `LICENSE.txt`(부록 A 재배포·부록 B cuBLAS 제3자 고지 포함)를 SHA-256 검증해 채운다.
  - `koja.runtime.LlamaServer.processEnvironment`는 `WhisperServer.environment`(D-060)와 같이 윈도우에서 실행 파일(PATH에서 찾은 단일 명령 이름 포함) 형제 `cuda/` 폴더가 존재하면 부모 환경의 대소문자 보존 `PATH`(보통 `Path`) 맨 앞에 붙인다. `LlamaServerClient`가 이를 `LocalServer` 환경에 전달한다.
  - `app/build.gradle.kts` `jpackage` `bundles`에 `"llama" to "llama-server$exe"`를 추가해 맥 `Contents/llama/`, 윈도우 `<설치 폴더>/llama/`로 넣는다. 윈도우 `jpackage`는 `llama/`·`whisper/` 안에 공유 CUDA DLL이 중복 잔류하면 실패시켜 이전 번들 잔재를 막는다. `.github/workflows/build.yml`은 `app/build/llama`만 별도 캐시(`llama-<OS>-<arch>-<스크립트 해시>`)해 `whisper`의 `app/build/cuda` 캐시와 충돌하지 않게 하고, 맥 `.dmg`·윈도우 `.msi` 검사에서 `llama/llama-server --version`(윈도우는 `cuda/`를 `PATH` 앞에 추가)·`llama/NOTICE.txt`·`llama/LICENSE`·CUDA DLL 비중복을 검증한다.
  - 맥 최소 버전: `llama.cpp b12655` 공식 macOS arm64 바이너리의 `minos`는 `13.3`이며(`bundle_llama.sh`에서 `vtool`로 검사), 이에 따라 맥 설치판의 실질 최소 지원 버전은 macOS 13.3 이상이다(기존 `ffmpeg`·`whisper-server`의 13.0보다 높음).
- **이유**: CUDA 런타임 DLL 약 575MB(압축 전) 중복을 없애고 `whisper-server`와 같은 공유 `cuda/`·고지·캐시 구조를 유지한다. NVIDIA 공식 `cuda/LICENSE.txt`가 CUDA 12.4 EULA 부록 B(cuBLAS 제3자 고지)를 이미 포함하므로 `llama/`에 별도 cuBLAS 고지 파일을 중복 보관하지 않아도 된다. 맥은 Apple Silicon 개인 사용(M5 Pro) 기준이라 13.0용 소스 빌드 대신 공식 13.3 바이너리를 유지한다.
- **버린 대안**: `llama/`에 CUDA DLL 중복 포함(설치파일 크기 증가), `bundle_llama.sh`가 매번 `app/build/cuda` 덮어쓰기(`bundle_whisper.sh` 캐시 무효화 및 391MB 재다운로드), 두 캐시에 `app/build/cuda` 중복 지정(CI 캐시 충돌).
- **확인 범위**: 맥 arm64에서 `./gradlew build`, `scripts/bundle_llama.sh`, `./gradlew jpackage` `.dmg` 마운트 후 `Contents/llama/llama-server --version`·`NOTICE.txt`·`LICENSE` 확인 완료(2026-11-26). 윈도우 CUDA 실행·통합 `.msi` 실기 확인은 D-068에 따라 W2-4 병합 직후 일괄 진행한다.

## D-071 M2 행: 구간 1개 = 행 1개, 한국어가 아닌 구간은 한국어 후보 + `TEXT_UNSURE`, 미확인 화자는 `SPEAKER_UNSURE`
- **결정**: M2에서는 LLM 없이 STT 구간 1개를 `LINE` 행 1개로 만든다(`koja.core.SegmentRows`). 행 id는 `r<구간 id>`, `segIds`는 그 구간 하나, `ignoredSegIds`는 비운다.
  - `ko`: `lang`이 `ko`면 `text`, 아니면 2회차 한국어 후보 `ko.text`(없으면 빈 문자열).
  - `ja`: `lang`이 `ja`면 1회차 원문 `text`, 그 밖에는 null. 번역은 M3 7단계가 채운다.
  - `startMs`: 고른 텍스트의 첫 단어 시각(단어가 없으면 구간 시작, D-040).
  - 플래그: `lang`이 `ko`가 아니거나 `ko`가 비면 `TEXT_UNSURE`. `speakerId`가 null이거나 화자표에서 `confirmed`가 아니면 `SPEAKER_UNSURE`.
  - 행은 `stages.rows`로 관리한다. STT·화자 구분을 다시 돌리기 전에 그 단계와 `stages.rows`의 완료 표시를 먼저 지워 저장하고, 화자 구분을 새로 돌렸거나 `stages.rows`가 없을 때만 행을 다시 만든다. 그 밖에는 사람이 고친 행을 그대로 둔다.
- **이유**: 절대 규칙 1(시간·원문은 STT에서만)과 2(모르면 비우고 표시)를 지키는 가장 단순한 행 구성이다. 한국어가 아닌 구간의 한국어 후보는 강제 한국어 전사라 번역에 가까울 수 있어 검수가 필요하다. 일본어 원문은 검수자가 들은 말과 맞춰 볼 수 있게 남긴다. 결과 파일을 쓰기 전에 완료 표시를 지워야, 새 `stt.json`·`diar.json` 저장 뒤 `project.json` 저장 전에 멈춰도 옛 완료 표시가 새 결과를 가리키지 않는다(옛 행이 새 구간 id를 가리키거나 옛 확정 화자 이름이 남는 일).
- **버린 대안**: 화자 붙이기 때마다 행 재생성(사람이 고친 행이 사라짐), 한국어가 아닌 구간을 무시 목록에 넣기(답변 누락 위험, D-045), 일본어 칸을 항상 비우기(검수 때 원문을 다시 들어야 함).

## D-072 처리는 가져오기 직후 자동 시작, 빠진 모델은 용량을 묻고 받으며, 취소는 엔진을 내린 뒤 창을 닫는다
- **결정**: 가져오기가 끝나면 검수 화면을 연 뒤 바로 처리 창(`koja.ui.PipelineDialog`)을 띄운다. 열린 프로젝트는 처리 메뉴 → 전사·화자 구분 실행(Ctrl/Cmd+R)으로 다시 돌린다(끝난 단계는 건너뜀, 저장 안 한 편집이 있으면 먼저 묻는다).
  - 처리 전에 `audio.wav`가 없으면 모델을 받지 않고 가져오기를 안내한다. 가져오기는 `stt.json`·`diar.json`이 있는 폴더도 거부한다(처리가 그 파일을 덮어쓴다).
  - 돌릴 단계(`Pipeline.pending`)에 필요한 모델만 본다(`LocalEngines.STT_MODELS`: whisper large-v3-turbo·Silero VAD, `DIAR_MODELS`: pyannote 분할·CAM++). 크기로만 설치 여부를 보고, 빠진 것이 있으면 개수·용량·저장 위치를 확인받은 뒤 `ModelStore`로 받는다. SHA-256은 sherpa 모델은 엔진을 열 때마다, whisper 모델은 받을 때 검사한다.
  - 취소는 `CancelToken` 취소 + 작업 스레드 interrupt다. 작업 스레드가 엔진을 닫고 끝난 뒤에 창이 닫히고, "끝난 단계와 받은 모델은 남아 있다"고 안내한다. 실패도 같은 안내에 오류 메시지를 붙인다. 취소·실패 뒤에는 검수 화면이 `project.json`을 디스크에서 다시 읽는다(옛 프로젝트를 저장해 끝난 단계 표시를 덮지 않게).
- **이유**: M2 완료 기준이 "영상 → 행이 검수 화면에 뜸"이라 별도 조작 없이 이어지는 편이 맞다. 1.7GB 다운로드는 사용자 동의 없이 시작하지 않는다. 창을 먼저 닫으면 서버가 내려가기 전에 다시 실행해 GPU를 둘이 쓸 수 있다(절대 규칙 5, `Pipeline` 잠금이 막지만 사용자는 멈춘 것처럼 본다).
- **버린 대안**: 매번 SHA-256 전체 검사(1.6GB 모델에서 실행마다 수 초), 설치 때 모델 동봉(설치파일이 1.7GB 커짐), 처리 강제 재실행 메뉴(M2 범위 밖, 결과 파일을 지우면 된다).
